# 21 Век: GPT с тулзами

| Task | Entrypoint | Customer |
|---|---|---|
| GPT с запросом оператора, сценарием заказа и завершением диалога | `gpt_21vek_tools.js` | 21 Век |

Отдельный вариант на основе промпта `../gpt_21vek.js` и реализации
`../../Craft/GPT Qwen/GPT TOOLS/`. Исходный агент не изменён.

## Поведение

- `transfer_to_operator`: просьба об операторе без намерения новой покупки,
  отсутствие подходящего контекста либо недостаток данных для корректного ответа.
  Открывает статью «Запрос оператора». При первом вызове статья может просить
  переформулировать вопрос, при повторном — переводить на оператора. Условия,
  счётчик повторов и слоты управляются статьёй. GPT не дублирует их и не обещает
  немедленное соединение. Если после переформулировки ответа всё ещё нет,
  тулза вызывается повторно; если контекст достаточен — GPT отвечает по нему.
- `create_order`: актуальное намерение купить или заказать товар, даже при
  найденном контексте. Открывает отдельную статью «Создать ЗК», которая сама
  подтверждает желание оформить заказ и переводит специалисту при согласии.
  Тулза запускает сценарий, а не создаёт заказ автоматически. Имеет приоритет
  над запросом оператора и завершением, в том числе для «соедините с оператором,
  хочу оформить заказ». Общий вопрос о правилах оформления можно отвечать
  по базе; уже совершённая покупка и отказ от покупки не означают новый заказ.
- `finish_dialog`: из истории видно, что клиент получил ответ, поблагодарил,
  новых и нерешённых вопросов нет. Одного «Ок», прощания или благодарности
  в начале разговора недостаточно. Благодарность с новым вопросом не завершает
  диалог. Покупка и просьба об операторе имеют приоритет.
- Обычный текстовый ответ LLM → статья `articles.AFTER_LLM_ANSWER.ID`.
  Это сохраняет переход после ответа из исходного агента. При любом
  `tool_calls` дополнительная статья и сопровождающий текст LLM не отправляются.
  Пустой ответ, ошибка и отмена обработки также не запускают эту статью.
- Все три тулзы открывают настроенные статьи сценариев в `aiassist_agent_id`
  через `/switchredirect`, как в шаблоне. Перед передачей управления очередь
  тулзов GPT очищается, чтобы следующий вопрос после статьи обрабатывался заново.
  Слоты и счётчики статьи при этом не изменяются. Статья завершения запускает
  принятый в проекте процесс завершения.

## Возврат из статьи «Создать ЗК»

Возврат поддерживается как новый текстовый запрос в том же диалоге. Статья
может передать текущий ввод клиента в aiassist2 через показанный в сценарии
`/switchredirect <ID aiassist2> {{__USER_INPUT__}}`; дальнейшая маршрутизация
должна направить вопрос в этот GPT-агент. Если статья возвращает управление
непосредственно GPT, используйте ID основного агента и текущий вопрос.
Передавайте новый вопрос, а не исходное «хочу купить» или служебную команду.

При запуске `create_order` GPT сохраняет служебную отметку
`gpt_21vek_create_order_return` в своём `dialogStorage`. На следующем текстовом
обращении отметка читается и удаляется. В промпт добавляется указание отвечать
на текущий вопрос, не повторяя оформление только из-за покупки в истории.
Факт возврата сам по себе не означает создание или отмену заказа.
Новое явное намерение купить позволяет снова вызвать `create_order`.

Перед обработкой нового вопроса также удаляется оставшийся от старой версии
вызов сценарной тулзы без ожидаемого результата. Это исключает продолжение
старого цикла через `/tool_responses`, которое могло игнорировать новый вопрос.
Слоты анкеты статьи и её счётчики GPT не изменяет.

После возврата доступны обычный ответ с последующей статьёй, запрос оператора
и остальные тулзы по их правилам. При вызове тулзы дополнительной статьи после
ответа нет. Сценарий не обязан записывать `scenario_result`.

Сохраняются дружелюбный тон, краткость до 300 символов и правила исходного
промпта. Противоречивые указания о переформулировке при нехватке данных заменены
вызовом статьи запроса оператора. Факты разрешено брать только из релевантного контекста. По умолчанию
используются розничные условия; оптовые — только при явном упоминании опта.
Несколько упаковок не означают оптовую покупку. Условия разных категорий
нельзя переносить друг на друга. Предыдущий контекст не подмешивается
(`ADD_OTHER_CONTEXT: false`).

## Подключение

`gpt_core.js` — единственный подключаемый модуль, скопированный из указанного
шаблона без изменений. Код модели Qwen из шаблона включён в начало основного
скрипта `gpt_21vek_tools.js`; там же находятся проектные переопределения.

Лимита размера скрипта нет, поэтому core подключается целиком.

1. Создайте один JS-модуль из `gpt_core.js`.
2. Создайте основной JS-агент из `gpt_21vek_tools.js`.
3. В поле подключаемых модулей основного агента укажите ID созданного модуля
   core. Отдельный модуль Qwen не нужен.
4. Загрузите `gpt_21vek_tools_settings.json` и заполните настройки окружения.

## Настройки

Из `../gpt_21vek_settings.json` перенесены адреса поиска и LLM, токен,
ID клиента и aiassist2, таймаут, температуры, параметры перефразирования,
thinking, отображения reasoning и фильтры базы знаний. Плоские ключи исходного
файла преобразованы во вложенный формат нового агента.

Настройки `agent_name`, `api.base_url` и коды статей заполняются отдельно:
в исходном файле их нет. Уже указанные в новом файле ID статей сохранены.
Для новой тулзы `articles.CREATE_ORDER.ID` заполнен предоставленным кодом статьи
«Создать ЗК». `api.url_mediator_service` нужен только
при включении истории через mediator. Секреты и значения окружения
в документации не приводятся.

| Настройка | Назначение |
|---|---|
| `api.base_url` | Полный URL CraftTalk с протоколом |
| `api.url_context_search`, `api.url_llm`, `api.llm_auth_token` | Поиск контекста и craftgpt с поддержкой тулзов |
| `api.url_mediator_service` | Адрес mediator, если история берётся через него |
| `customer_id`, `agent_name` | Клиент и ID нового GPT-агента |
| `aiassist_agent_id` | Экземпляр aiassist2, содержащий все четыре статьи сценариев |
| `articles.TRANSFER_FOR_OPERATOR.ID` | Код статьи «Запрос оператора» с собственной логикой переформулировки и повторного обращения |
| `articles.CREATE_ORDER.ID` | Код отдельной статьи «Создать ЗК» |
| `articles.FINISH_DIALOG.ID` | Код статьи завершения |
| `articles.AFTER_LLM_ANSWER.ID` | Код статьи, вызываемой после обычного ответа в исходном агенте |
| `context_settings.CATALOG_IDS` | Прежний `catalog_id` как массив из одного элемента; пустое значение преобразовано в `null` |
| `context_settings.RECORD_TYPE` | Прежний `record_type` |

Обязательны `USE_HISTORY: true`, `SMALLTALK_IF_NO_CONTEXT: true` и
`ADD_OTHER_CONTEXT: false`. Агент проверяет их перед обработкой. При пустом
контексте используется тот же строгий промпт и все три тулзы: это позволяет отличить
приветствие, намерение покупки или завершённый разговор от вопроса, требующего оператора.
Статические сведения о компании из старого smalltalk-промпта не используются.
Прежние `enable_smalltalk` и `redirect_back_to_aia2` не переносятся: выбор
сценария и переход после ответа выполняются новой логикой тулзов и статей.

История по умолчанию передаётся в craftgpt через `dialog_id`, как в исходном
агенте. Сервис должен возвращать историю текущего диалога. Если используется
mediator, включите `HISTORY_FROM_BOT_MEDIATOR` и настройте его URL.

## Вход, выход и ошибки

Обрабатываются текстовые сообщения `message_type === 1`. Остальные типы, включая
старт и системные события, завершаются `resolve([])` без вызова сервисов.
Специальные входные слоты не требуются; служебные слоты и очередь тулзов
поддерживаются core через `slot_context` и `agentStorage.dialogStorage`.
Отметка возврата из заказа хранится отдельно в том же `dialogStorage`.

Ответы отправляются через `agentApi.sendMessage`, затем entrypoint вызывает
`resolve([])`. При ошибках core пишет диагностику и отправляет стандартный текст
ошибки; переход к статье после ответа не выполняется. Незаполненные ID сценариев
блокируют обработку до обращения к LLM. Защитные проверки внутри самих тулзов
выбрасывают исключение: подробности ошибки не передаются модели как результат тулзы.

## Проверка

Из корня репозитория:

```powershell
node --check '21 Vek/tools/gpt_21vek_tools.js'
node --test '21 Vek/tools/gpt_21vek_tools.test.cjs'
```

Тесты выполняют модуль core вместе с основным скриптом в VM с подменёнными API, axios и хранилищем,
без сетевых вызовов. Они проверяют маршрутизацию, порядок ответа и статьи,
подавление текста при тулзах, ошибки и пропуск событий. Ответы LLM в них заданы
заранее: семантический выбор тулзы и качество ответов требуют проверки на
реальной модели в тестовом окружении.

Проверьте там: первый и повторный запрос оператора; новый вопрос после
переформулировки; возврат из «Создать ЗК» с вопросом о доставке; повторное
намерение покупки после возврата; покупку холодильника; заказ нескольких
упаковок минваты; розничный вопрос при найденных только оптовых условиях;
вопрос без контекста; благодарность после ответа; «Спасибо, а сколько стоит
доставка?»; «Спасибо, но вопрос не решён»; благодарность в начале разговора;
«соедините с оператором, хочу купить холодильник»; «я уже купил холодильник,
как вернуть?». Покупки должны открывать статью «Создать ЗК», прочие запросы
оператора — статью «Запрос оператора».
Для обычного ответа должна запускаться только статья после ответа, для тулзы —
только соответствующий сценарий.
