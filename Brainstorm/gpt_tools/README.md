# BRAINSTORM GPT Agent

| Task | Entrypoint | Customer |
|---|---|---|
| Поддержка оборудования BRAINSTORM и маршрутизация обращений | `gpt_brainstorm.js` | BRAINSTORM |

`gpt_brainstorm` - единый GPT-агент поддержки BRAINSTORM. Он принимает вопрос клиента без предварительного выбора кнопками, определяет линейку оборудования и ищет ответ только в соответствующем разделе базы знаний.

## Назначение

Агент заменяет прежнюю схему из отдельных агентов, где клиент сначала выбирал категорию оборудования, а затем перенаправлялся к одному из них. Теперь классификация выполняется моделью по тексту вопроса. Если линейку определить нельзя, агент запрашивает бренд и модель, а не выполняет поиск по похожему оборудованию.

Поддерживаемые линейки:

| Линейка | `product` для поиска | Очередь оператора | Примеры моделей |
|---|---|---|---|
| TPMSMAN | `grunbaum` | `tpmsman` | Датчики и программаторы TPMSMAN |
| AUTEL TPMS | `autell` | `autel` | MaxiTPMS |
| AUTEL Diagnostic | `autel_diag` | `диагностическое` | MaxiSYS, MaxiDAS, MaxiIM, MaxiBAS, Maxivideo, ADAS |
| LAUNCH | `launch` | `диагностическое` | X-431 PAD/PRO, BST, CReader, ADAS |
| JALTEST | `jaltest` | `диагностическое` | Диагностическое оборудование JALTEST |
| ICEMAN | `iceman` | `сервисное` | АС8000S, АС7000S, АС7000S Basic, АС7500S, AC2000N, AC3000N |
| INJMAN | `injman` | `сервисное` | INJ6000N GDI, INJ6000 |
| SERVICEMAN | `serviceman` | `сервисное` | ATF4000N, BRK3000, CLT3000 |

Оборудование Topdon, Thinkdiag, THINKCAR, TEXA, Scandoc, THINKTOOL, CARMAN SCAN, MaxiAP AP200, AUTEL EVO и OTOFIX не поддерживается. При явном упоминании такого оборудования агент сообщает об этом без поиска в базе знаний и без технических рекомендаций.

## Состав

```text
Brainstorm/gpt_tools/
├── gpt_brainstorm.js            # Входной скрипт и логика BRAINSTORM
├── gpt_brainstorm_settings.json # Параметры окружения и маппинг продуктов
├── gpt_core.js                  # Собранное ядро gpt-modular
└── gpt_qwen.js                  # Адаптер модели Qwen
```

В CraftTalk `gpt_core` и `gpt_qwen` подключаются к `gpt_brainstorm` как JS-модули. Редактировать логику BRAINSTORM следует в `gpt_brainstorm.js`; `gpt_core.js` является копией собранного общего ядра.

## Поток обработки

1. Агент получает текст вопроса и историю диалога.
2. Если в вопросе есть просьба об операторе или менеджере, очищается очередь незавершённых tool-вызовов и выполняется перевод на оператора.
3. Для обычного сообщения модель получает промпт с перечнем поддерживаемых продуктов и инструментов.
4. Если клиент хочет подобрать TPMS-датчик, модель вызывает `select_sensor` и переводит диалог на статью-сценарий подбора.
5. Для вопроса об оборудовании модель определяет ровно один `product`. При неоднозначности она просит назвать бренд и модель.
6. Модель вызывает `search_in_knowledge_base` с тремя русскоязычными запросами: текущим вопросом с исходным названием оборудования и фактами из истории, точной переформулировкой и вариантом первого запроса с нормализованным названием модели из справочника. Нормализация исправляет только однозначные опечатки, транслитерацию и формат записи; не меняет модель, суффикс, бренд, продукт и код ошибки. Если нормализация не нужна или соответствия нет, третий запрос — ещё одна точная переформулировка. Неоднозначную модель нужно уточнить до поиска.
7. Инструмент ищет контекст с выбранным `record_type`, удаляет из статей навигационные элементы, сохраняет очередь оператора в слоте `queue` и передаёт контекст модели.
8. Ответ строится только на основе найденного контекста выбранной линейки и модели. При нехватке конкретных сведений задаётся адресный вопрос; если после уточнения и повторного поиска решения нет или материалы исчерпаны, выполняется перевод оператору.

Приветствия, благодарности и простые общие вопросы обрабатываются кратко, без инструментов.

## Копия с уведомлением перед поиском

| Task | Entrypoint | Customer |
|---|---|---|
| Уведомление о поиске без ожидания завершения агента | `gpt_brainstorm_search_notice.js` | BRAINSTORM |

`gpt_brainstorm_search_notice.js` — отдельная копия основного агента с тем же промптом и инструментами. Подключаются те же модули `gpt_core.js` и `gpt_qwen.js`; формат настроек соответствует `gpt_brainstorm_settings.json`. Основной `gpt_brainstorm.js` уведомление не отправляет.

Перед первым поиском копия сохраняет маркер вызова в `agentStorage.dialogStorage` и выполняет `/switchredirect` на `articles.SEARCH_NOTICE.ID` через экземпляр из `search_notice.aiassist_agent_id`. Значение экземпляра по умолчанию в файле настроек соответствует прежнему `switchredirect()` ядра; для другого окружения задайте нужный ID. Сценарий выводит «Подождите немного, уже ищу ответ.» и возвращает управление **тому же экземпляру JS-агента, в котором размещена копия**. Переход обратно должен оставлять диалог на этом агенте. Код основного агента не поддерживает это продолжение.

Исходная очередь с `product`, `queries` и `toolCallId` сохраняется. После возврата выполняется отложенный поиск, а его результат передаётся ЛЛМ как результат исходного вызова тулзы. Повторного запроса к ЛЛМ для выбора продукта нет. Дополнительные поиски в рамках продолжения не показывают уведомление снова. При завершении, отмене или ошибке маркер удаляется. В режиме отчёта (`IS_QUERY_REPORT`) переход отключён. Если сценарий не возвращает управление, поиск остаётся ожидающим в очереди.

Копия локально расширяет `RedisQueue`: специальное исключение преобразуется в платформенный переход за пределами `runToolsLoop`, поэтому ветка очистки очереди при обычном редиректе не срабатывает. Общий `gpt_core.js` не изменяется. Фактическую доставку уведомления до ответа необходимо проверить в рабочем канале: немедленный возврат из сценария сам по себе не подтверждает отсутствие буферизации платформы.

Изолированные проверки: `node --test 'Brainstorm/gpt_tools/gpt_brainstorm_search_notice.test.cjs'`. Они выполняют реальный код очереди и цикла инструментов с подменёнными платформенными глобальными объектами и HTTP: два запуска с сохранением аргументов и ID тулзы, дополнительный поиск без нового уведомления, режим отчёта, отсутствие конфигурации, отмена и ошибка HTTP. Внешние сервисы не вызываются.

## Инструменты

| Инструмент | Когда вызывается | Результат |
|---|---|---|
| `search_in_knowledge_base` | Вопросы по использованию, настройке, прошивке, диагностике и ошибкам известной линейки | Запрос в contextsearch только по одному `record_type`; запись очереди в слот `queue` |
| `select_sensor` | Клиент хочет найти, выбрать или подобрать TPMS-датчик, в том числе без модели автомобиля или парт-номера | `switchredirect` на статью подбора датчика |
| `transfer_to_operator` | Явная просьба об операторе/менеджере, отсутствие решения после уточнения и повторного поиска или исчерпание материалов | `switchredirect` на статью перевода с заполненным слотом `queue` |

Значение `queue` устанавливается после успешного поиска по продукту. Если продукт ещё не определён, при переводе используется очередь `другое`.

## Правила ответа

- Не смешивать материалы разных брендов, линеек и моделей.
- Не подменять отсутствующую информацию внутренними знаниями модели.
- Не искать по другому продукту, если в выбранной базе нет ответа.
- Не раскрывать клиенту названия инструментов, значения `product`, `record_type`, `queue` или техническую логику маршрутизации.
- При точном совпадении статьи с запросом дать ссылку и кратко описать её содержание.
- Не переносить в ответ кнопки, меню и навигационные блоки из статей.
- Распознавать бренд по однозначной модели из справочника, в том числе `DS808`, `DS808BT` и `Ts508`; `MS906TS` искать в `autell`. Отсутствие модели в справочнике не означает отказ в поддержке.
- Учитывать историю, ответы на уточнения и результаты проверок. Не спрашивать известный бренд повторно и не повторять неработающий совет; явная смена прибора меняет контекст оборудования.
- Указывать страницы, пункты, названия и ссылки только при их наличии в найденном источнике. Упоминание PDF не подтверждает доступность его содержимого.
- Завершать незавершённую диагностику следующим подтверждённым шагом или конкретным вопросом, без обязательной фразы «Могу ли чем-то ещё помочь?».

## Настройки

Основные настройки находятся в `gpt_brainstorm_settings.json`.

| Раздел | Назначение |
|---|---|
| `api` | URL craftgpt, contextsearch и ботмедиатора; токен доступа к LLM |
| `customer_id`, `agent_name` | Идентификатор проекта и имя агента |
| `llm_settings` | Таймаут, температура и параметры генерации Qwen |
| `context_settings.MAX_CONTEXTS` | Максимальное число статей, передаваемых после поиска |
| `agent_parameters` | История диалога, отладка, лимит tool-цикла и флаги reasoning |
| `products` | Единый источник маппинга `product` -> название, описание и очередь оператора |
| `articles` | ID статей для перевода оператору, подбора датчика и уведомления о поиске (`SEARCH_NOTICE`) |

Чтобы добавить новую линейку, нужно одновременно:

1. Добавить её в `products` с уникальным ключом `product`, описанием и очередью.
2. Добавить линейку и модели в системный промпт `gpt_brainstorm.js`.
3. Убедиться, что contextsearch содержит материалы с тем же `record_type`.
4. При необходимости настроить очередь в сценарии статьи перевода оператору.

Не публикуйте в документации и не передавайте в клиентский скрипт значения токенов из `api.llm_auth_token`.

## Отличия от стандартного gpt-modular

Базовая архитектура предоставляет общее ядро: загрузку истории, стандартный RAG, tools-loop, слоты, форматирование ответов и адаптеры моделей. `gpt_brainstorm` использует это ядро и Qwen, но переопределяет логику, необходимую для мультипродуктовой поддержки.

| Область | Стандартный `gpt-modular` / `gpt_tools.js` | `gpt_brainstorm` |
|---|---|---|
| Получение контекста | До вызова модели автоматически запускает `getContext()` с общими `RECORD_TYPE`, `CATALOG_IDS` и фильтрами | Отключает автоматический RAG при первом вызове; модель сама выбирает продукт и вызывает поиск через tool |
| Выбор базы знаний | Обычно задаётся настройками агента или ищется по общему контексту | Динамически определяется из вопроса, но строго ограничен одним значением из `agentSettings.products` |
| Поисковый запрос | Может использовать исходный текст и опциональные rephrase ядра | Текущий вопрос с фактами из истории, переформулировка и вариант с однозначно нормализованной моделью (либо ещё одна переформулировка) |
| Работа без контекста | При включённом smalltalk может отвечать без базы знаний | Передаёт модели синтетический контекст каталога, чтобы она вызвала нужный инструмент, а не отвечала по общим знаниям |
| Тулзы | Базовый пример содержит перевод оператору и универсальный перевод на сценарий | Добавляет поиск по конкретному продукту, специализированный подбор TPMS-датчика и перевод оператору с очередью |
| Маршрутизация оператору | Стандартный перевод не выбирает профильную очередь сам | После поиска сохраняет `queue` по продукту; сценарий перевода использует этот слот |
| Ограничения домена | Определяются промптом конкретного клиентского скрипта | Явно запрещает смешивать линейки, отвечать по неподдерживаемым брендам и использовать знания вне найденного контекста |
| Обработка статей | Использует стандартное форматирование контекста | Удаляет из содержимого статьи блоки навигации и очищает ответ от фраз о кнопках и меню |
| Диагностика | Логирование определено ядром | Дополнительно пишет тело запросов к craftgpt в debug-логи |

Переопределение `sendMessageToLLM()` необходимо для tool-first схемы. В инструментальном режиме craftgpt преобразует вызовы tools через эндпоинт `/context_query` только при непустом контексте, поэтому агент создаёт служебный синтетический контекст с каталогом продуктов. Этот контекст не содержит ответа для клиента и нужен только для корректного вызова инструментов.

## Проверка после изменений

Проверяйте как минимум следующие сценарии:

| Вопрос клиента | Ожидаемый результат |
|---|---|
| `Как обновить прошивку на TS508?` | Поиск по `autell` |
| `Ошибка -6 на аутел тс508` | `autell`; третий запрос: `Ошибка -6 на AUTEL MaxiTPMS TS508`, с сохранением исходного обозначения в первом запросе |
| В названии модели неоднозначная опечатка | Уточнение модели до поиска; без подстановки другой модели или суффикса ради совпадения |
| `Не могу запрограммировать датчик` → `Ts508` → `Ошибка -6` | Поиск по `autell` с TS508, программированием и ошибкой; без повторного вопроса о бренде |
| `Не работает DS808` / `DS808BT` | Поиск по `autel_diag`, без отказа в поддержке и без смешивания вариантов модели |
| `Как обновить MS906TS?` | Поиск по `autell`, несмотря на название MaxiSYS |
| `Как пользоваться MaxiSYS MS906?` | Поиск по `autel_diag` |
| `Как настроить X-431 PAD V?` | Поиск по `launch` |
| `Инструкция для ATF4000N` | Поиск по `serviceman` |
| `Ошибка на INJ6000N GDI` | Поиск по `injman` |
| `Подберите датчик на Kia Rio` | Переход в сценарий подбора датчика |
| `У меня Topdon, помогите` | Сообщение о неподдерживаемом оборудовании без поиска |
| `Как откалибровать датчик?` | Запрос бренда и модели, без поиска до уточнения |
| `Соедините с менеджером` | Перевод оператору |
| `Датчик заблокирован` на TS508; в БЗ нет решения | Без догадок про SGW/SFD, пароль экрана и VCI; адресное уточнение, затем перевод при отсутствии решения |
| Ответ клиента на вопрос о проверке: `Проверил, не помогло` | Учесть результат и дать следующий подтверждённый шаг; без повтора прежнего списка |
| `Теперь вопрос про X-431 PRO` после TS508 | Смена продукта на `launch`, без переноса ошибки TS508 |
| По INJ6000N GDI найдена только ссылка на PDF без текста и нумерации | Без вымышленных страниц, пунктов и утверждений о содержимом PDF |

Эти сценарии проверяются с моделью и контролируемой БЗ; `node --check` проверяет только синтаксис. История включается настройками `USE_HISTORY`; при `HISTORY_FROM_BOT_MEDIATOR: false` загрузка истории делегируется craftgpt (передаётся `history: null`). Сам промпт не восстанавливает историю, отсутствующую на сервере.
