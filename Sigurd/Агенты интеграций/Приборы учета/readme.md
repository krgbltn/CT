# Приборы учета

JS-агенты получают сведения о приборах учета и типе дома из REST API СИГУРД. Агенты приема и передачи показаний описаны отдельно в `Прием показаний/readme.md`.

| Task | Entrypoint | Customer |
|---|---|---|
| Проверка электросчетчика | `check_device.js` | СИГУРД |
| Проверка услуги и прибора по ЛС | `check_service_device.js` | СИГУРД |
| Проверка типа дома | `check_housetype.js` | СИГУРД |
| Проверка даты поверки | `device_verification_check.js` | СИГУРД |
| Получение последнего показания | `last_reading_get.js` | СИГУРД |
| Последние показания по всем приборам ЛС | `get_all_last_readings.js` | СИГУРД |

## Агенты

### check_device

Проверяет наличие выбранного слотом `device` прибора электроснабжения для ЛС `uid`. При успехе передает сведения о приборе: `device`, `service_name`, `city`, `house_type`, `readings_accept_type` и `final_answer: "1"`. Если прибор не найден, передает `final_answer: "2"`.

### check_service_device

После идентификации принимает `uid` выбранного ЛС и `service_type` — одно из значений: `Электроэнергия`, `Холодное водоснабжение`, `Горячее водоснабжение`, `Отопление`. Сценарий нормализует слова клиента до одного из этих значений; слот `device` здесь не используется (в других агентах он хранит ID прибора).

Вызывает GET `/api/service/sigurd/fl/{uid}/info`. Услуга проверяется по точному совпадению в `account.accounts[].services[]` **для `account.number`**; приборы — по `account.devices[].service_name` согласно алиасам из настройки `serviceNames`. В ответ передаются строковые слоты `"true"` / `"false"`:

| Слот | Условие для `"true"` |
|---|---|
| `service_exists` | услуга есть в списке услуг выбранного ЛС |
| `service_active` | услуга найдена и хотя бы у одного её прибора `service_active === true` |
| `device_exists` | найден хотя бы один прибор для услуги |
| `device_active` | хотя бы у одного подходящего прибора `accepts_readings === true` |

Если признак активности отсутствует, слот получает `"false"`. Значение `service_active: "false"` при отсутствии приборов означает **«активность не подтверждена»**, а не доказанное отключение услуги. Статус всего ЛС (`/info.status`) не подменяет статус отдельной услуги. Для сценария `device_active` означает, что по прибору разрешён приём показаний (`accepts_readings === true`). При `accepts_readings === false` прибор считается недействующим для сценария, хотя причина запрета может быть не только снятием с расчётов. `readings_accept_type` по-прежнему передаётся как диагностическое значение.

При наличии данных также передаёт `service_name`, `city`, `readings_accept_type`. Если прибор найден, GET `/{uid}/disconnection_report_info` даёт `house_type` из `housetype`. При ошибке запроса, некорректном ответе, незаполненном `uid` или неизвестном `service_type` переводит на оператора, не записывая четыре слота как `false`. HTTP-настройки, статьи и авторизация задаются в `check_service_device_settings.json`; `authorizationToken` нужно заполнить при развёртывании.

### check_housetype

Получает тип дома для ЛС `uid`. Передает значение в `housetype` и `final_answer`: `1`, если тип определен, иначе `2`.

### device_verification_check

После идентификации получает `uid` и нормализованный сценариями `service_type`: `Электроэнергия`, `Холодное водоснабжение`, `Горячее водоснабжение` или `Отопление`. Одним запросом GET `/api/service/sigurd/fl/{uid}/info` находит первый прибор, соответствующий услуге по `service_name` и алиасам из настройки `serviceNames`. Передаёт `next_check` и `final_answer`: `"1"`, если прибор и дата следующей поверки найдены; `"2"`, если прибор или дата не найдены. Слот `device` не требуется и не заполняется; дата не сравнивается с текущим днём.

### last_reading_get

Находит прибор для услуги из слота `service_type` и передает `device`, `last_reading` и `last_reading_date`.

### get_all_last_readings

После идентификации получает `uid` выбранного ЛС. Услугу или прибор у клиента уточнять не нужно. Вызывает GET `/api/service/sigurd/fl/{uid}/devices`, обходит все приборы и берёт **только** `last_reading.readings[0]` каждого прибора. Шкала не используется. Показание с отсутствующим значением или датой считается отсутствующим; значение `0` учитывается. Приборы без показаний остаются в `devices_readings`, но не включаются в текст вопроса.

| Слот результата | Значение |
|---|---|
| `final_answer` | `"1"` — есть хотя бы одно полное показание; `"2"` — приборов нет; `"3"` — приборы есть, но ни у одного нет показания с датой |
| `readings_text` | При `"1"` готовый вопрос: «По вашему лицевому счёту последние показания: прибор № … — … от …; прибор № … — … от …. Вы передавали эти показания?»; иначе пустая строка |
| `devices_readings` | JSON-массив `{device_id, device_number, service_name, last_reading: {value, date} | null}` для каждого прибора; при отсутствии приборов `[]` |

Для ISO-даты при озвучивании используется формат `ДД.ММ.ГГГГ`; дата в `devices_readings` остаётся как в API. Дата в `/devices` — дата передачи показания, поэтому вопрос не утверждает, кто его внёс. Сценарий озвучивает `readings_text` только при `final_answer = "1"` и затем обрабатывает ответ «да/нет». При ошибке API, неверной форме ответа или отсутствии `uid` агент переводит на оператора. Статьи, URL и авторизация задаются в `get_all_last_readings_settings.json`; токен авторизации взят из настроек соседнего `last_reading_get`.

## Маршрутизация

Все агенты получают ID ИИ-агента из слота `classifier`. Целевая статья берется из `next_article`; если слот не заполнен, используется `nextArticle` из настроек. При ошибке запроса или неполных обязательных данных диалог направляется в статью `operatorArticle`.
