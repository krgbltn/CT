# Прием показаний по всем счетчикам

 Решение выбирает один лицевой счет (ЛС), получает все приборы четырех услуг и последовательно принимает все их уникальные шкалы. Каждое подтвержденное показание отправляется отдельно. Реплики и подтверждения выполняются сценариями CraftTalk; очередь, проверка и отправка — JS-контроллером.

| Task | Entrypoint | Customer |
|---|---|---|
| Поиск и выбор ЛС по телефону | `identification_phone.js` | СИГУРД |
| Поиск и выбор ЛС по цифровой части номера | `identification_account.js` | СИГУРД |
| Очередь шкал, проверка, пропуск и передача | `readings-controller.js` | СИГУРД |
| SOAP-функции контроллера, подключаемый модуль | `readings-soap-module.js` | СИГУРД |


## Цепочка

Настроены семь основных сценариев: старт приема, результат телефонной идентификации, ввод номера ЛС, результат идентификации по ЛС, подтверждение адреса, общий прием и итог. Техническая ошибка использует существующую статью помощи/оператора; отдельная восьмая статья приема для нее не требуется.

```text
Старт (1–25 число) → идентификация по телефону → результат
  ЛС не найден → ввод и подтверждение номера → идентификация по ЛС → результат
  ЛС выбран → подтверждение адреса → «Начнем?» → init
    ready → готовность → ввод → подтверждение → process
    invalid → исправление той же шкалы → подтверждение → process
    accepted → сообщение об успехе → next → следующая шкала / итог
    отказ от прибора → skip_service=true + process → следующий прибор / итог
  итог → другой ЛС через ручную идентификацию / завершение
Техническая ошибка → помощь, без автоматической повторной передачи
```

Вопрос содержит услугу, последние три символа номера и прошлое показание; название шкалы по принятому решению не произносится. Учет и отправка по-прежнему ведутся отдельно по каждой шкале. Ошибки 1/2 допускают одно исправление с меткой сценария; 3/4 — повтор ввода без счетчика. Контроллер попытки не считает.

## Подключение и настройки

1. Создать SOAP-модуль, включить признак модуля и подключить его к контроллеру. Самостоятельно модуль не вызывать.
2. Перенести оба агента идентификации вместе с соответствующими `_settings.json`. У телефона `useHardcodedPhone` должен быть `false`.
3. Сверить SOAP-контур и маршруты в трех файлах настроек. Они содержат заполненные значения локальной конфигурации, а не пустые шаблоны; не переносить их между средами без сверки.
4. У контроллера `articles.input` и `articles.correction` указывают на одну общую статью, `articles.error` — на помощь, `articles.finish` — на итог. Все четыре поля обязательны, даже при совпадении первых двух. Статьи задаются через symbolCode, агенты — через ID экземпляров.
5. Зарегистрировать и сохранить слоты , особенно текстовый `readings_step_id`. Все вызовы цикла направить в один экземпляр контроллера и выполнять последовательно.

| Настройка контроллера | Назначение и текущее значение правила |
|---|---|
| `url` | Полный SOAP endpoint, не URL WSDL и не REST |
| `timeoutMs` | Положительное целое; в локальных настройках 30000 мс |
| `rejectUnauthorized` | Проверка TLS; в локальном JSON сейчас `false`, при отсутствии этого значения код проверяет сертификат |
| `aiAgent`, `routingAgent` | Агент сценариев и резервный маршрут помощи |
| `articles` | Четыре обязательных маршрута, описанные выше |
| `maxConsumption` | Общий предел прироста; сейчас строка `"100"`, фиксируется на цикл |
| `services` | Порядок: электроэнергия 24, ГВС 2, ХВС 21, отопление 1 |
| `slots` | Соответствие логических ключей фактическим ID слотов |

У идентификаций `classifier` переопределяет `aiAgent`, `next_article` — `nextArticle`. Контроллер эти входные маршруты не использует. В локальных JSON обеих идентификаций сейчас одинаковый `nextArticle`, тогда как в описанной цепочке есть отдельные статьи результата телефона и ЛС. При сопровождении сверять эффективный маршрут с учетом входного `next_article`.

## Ключевой контракт

Все значения слотов — строки. Пять общих полей результата идентификации: `account_id`, `account_number`, `account_address`, `successful_identification`, `address_success`. `account_id` берется из `ContractInfo.ID`, а не из номера ЛС. Идентификация не загружает приборы, не заполняет `electroScale` и старые группы показаний; она очищает их через `resetSlots`.

| Действие | Что передать контроллеру | Ответ |
|---|---|---|
| `init` | Действие, GUID/номер/адрес ЛС, стандартный `message.id` | Первая шкала `ready` или итог при пустой очереди |
| `process` | GUID ЛС, полученный `readings_step_id`, подтвержденный `current_new_reading` либо `skip_service="true"` | `accepted`, `invalid`, следующий прибор при пропуске либо технический маршрут |
| `next` | GUID ЛС и ID уже принятой шкалы | Следующая шкала `ready` либо итог |

`readings_action` формирует сценарий; `reading_status` и `readings_step_id` — контроллер. ID возвращается без изменений и не стирается при очистке ввода. На `invalid` использовать новый ID из ответа. `scale_type="true"` только при `MDSDigitsAfterDot=0`, иначе `"false"`; вид предыдущего показания на это не влияет.

Контроллер получает приборы параллельно по услугам, но строит очередь в порядке `services`, затем приборов и шкал ответа. Дубли `MDScaleID` исключаются без учета регистра, сохраняется первая запись. Пропуск относится к оставшимся шкалам текущего исходного прибора. Счетчики считают шкалы.

Допускается неотрицательное число с точкой/запятой в пределах точности шкалы, не меньше предыдущего, не больше предыдущего плюс порог и не больше максимума API. Ошибки: `1` — меньше предыдущего, `2` — превышен предел, `3` — формат, `4` — лишняя дробная точность. Успех объявляется только после `InputOfReadingsWithDotResult=1` и сохранения результата в `dialogStorage`.

При неизвестном результате, явном отказе API или состоянии `sending` автоматического повторного POST нет. Новый `init` с новым `message.id` начинает новый цикл, поэтому не использовать его как повтор отправки после сбоя. Подробности и ограничения защиты от повторов — в техническом описании.
