# Прием показаний по всем приборам и шкалам

Копии агентов этого каталога идентифицируют выбранный лицевой счет. Затем один контроллер последовательно принимает все уникальные шкалы его приборов. Каждое подтвержденное значение отправляется отдельно; следующая шкала подготавливается после сообщения сценария об успехе.

| Task | Entrypoint | Customer |
|---|---|---|
| Поиск и выбор ЛС по телефону | `identification_phone_number.js` | СИГУРД |
| Поиск и выбор ЛС по номеру | `identification_account_number.js` | СИГУРД |
| Очередь, проверка и отправка | `readings-controller.js` | СИГУРД |
| SOAP-функции, подключаемый модуль | `readings-soap-module.js` | СИГУРД |
| Прежняя отправка четырех фиксированных показаний | `submit-readings.js` | СИГУРД |

`submit-readings.js` сохранен для прежней цепочки. В новом сценарии его не вызывать. Отдельная инструкция статей и реплик: [scenario-plan.md](scenario-plan.md).

## Идентификация

По телефону вызывается `GetContractsInfo_By_Phone`, по цифровой части номера ЛС - `FindAllByContractNumber`. Получение приборов из этих копий удалено. После выбора передаются `account_id` из `ContractInfo.ID`, `account_number`, `account_address`, `successful_identification`, `address_success`.

Сохранены правила выбора адреса: единственный выбирается сразу; несколько - через сопоставление, подтверждение частичного совпадения или список. `address_success = "true"` только после подтвержденного частичного совпадения. При одинаковом адресе используется первый ЛС из ответа, как раньше. Кандидаты хранятся в собственном `dialogStorage` идентификации только до выбора.

Новый поиск, уточнения, пустой результат и ошибки очищают прежние выходные слоты ЛС и приборов. В `slots` агентов идентификации остаются только пять полей результата:

| Ключ | Слот |
|---|---|
| `accountId` | `account_id` |
| `contract` | `account_number` |
| `address` | `account_address` |
| `authSuccess` | `successful_identification` |
| `addressSuccess` | `address_success` |

`resetSlots` - отдельный объект `{ "ID слота": "значение сброса" }`. Он не описывает результат поиска: перед каждым ответом он очищает данные текущей шкалы и прежние группы `number_*`, `recent_*`, `scale_*`, `scale_id_*`, `readings_*`. Для `has_next_account` задан сброс в `"false"`, для остальных - пустая строка. Автоматического обхода найденных ЛС нет. Старые слоты можно исключать из `resetSlots` после полного отказа от прежней цепочки; поля нового цикла оставлять для очистки.

Пустой корректный поиск возвращает `successful_identification = "false"` в следующую статью; ошибки ведут в прежний маршрут оператора. Настройки `aiAgent`, `routingAgent`, `operatorArticle`, `nextArticle` и приоритет входных `classifier` / `next_article` сохранены. В контроллере маршруты задаются только настройками.

Подстановки приборов и выбор тестового ЛС через непустой `debug` удалены. У телефонной идентификации сохранен существующий переключатель `useHardcodedPhone`; для обычного запуска он должен оставаться `false`.

## Подключение на платформе

Порядок продуктивной выкладки, проверки и отката: [deploy-prod.md](deploy-prod.md).

1. Создать JS-агент с кодом `readings-soap-module.js` и включить «Является ли данный script модулем».
2. Создать агент с кодом `readings-controller.js`; в «Подключаемые js-script модули» указать фактический ID SOAP-модуля. Модуль отдельно не вызывается и не содержит `resolve()`.
3. Заполнить `readings-controller_settings.json` для тестового контура. Пустые URL и ID намеренно не содержат настроек существующего развертывания.
4. Создать статьи по [плану сценария](scenario-plan.md), заполнить их symbolCode в `articles`, ID экземпляра агента сценариев - в `aiAgent`.
5. Обновить обе копии идентификации вместе с настройками. Выход успешной идентификации направить в стартовый блок нового сценария, сохранив ветку неуспешного поиска.
6. Проверить на стенде весь цикл и переключить входную цепочку с четырех прежних сценариев на общий.

Без URL, `aiAgent` и всех четырех статей контроллер не обращается к SOAP. Если технический маршрут не настроен, используется `routingAgent`; при отсутствии обоих возвращается текст об ошибке. Системные сообщения, включая тип `200`, подтверждаются без отправки показаний.

## Настройки контроллера

| Настройка | Назначение |
|---|---|
| `url` | SOAP endpoint нужного контура |
| `timeoutMs` | Положительный целочисленный тайм-аут HTTP, в шаблоне 30000 |
| `rejectUnauthorized` | Проверка TLS-сертификата, по умолчанию включена; настройку внутреннего сертификата согласовать при подключении |
| `aiAgent` | ID экземпляра агента сценариев |
| `routingAgent` | Резервный маршрут при недоступной настройке технической статьи |
| `articles.input` | Общая статья ввода и сообщения об успехе |
| `articles.correction` | Статья исправления |
| `articles.error` | Техническая ошибка |
| `articles.finish` | Завершение ЛС и предложение другого ЛС |
| `maxConsumption` | Неотрицательная десятичная строка, по умолчанию `"100"`; фиксируется при начале цикла |
| `services` | Упорядоченный массив `{ code, name }` |
| `slots` | Соответствие логических ключей фактическим ID слотов |

Порядок услуг в шаблоне: электроэнергия (`24`), ГВС (`2`), ХВС (`21`), отопление (`1`). Названия для реплик: «электроэнергии», «горячей воды», «холодной воды», «отопления».

Запросы приборов параллельные, но очередь формируется по `services`, затем в порядке приборов и шкал ответа. Повторный `MDScaleID` включается один раз без учета регистра: сохраняется первая запись. Дополнительные правила объединения конфликтов не вводились. Разные исходные приборы с одинаковым номером не объединяются.

## Контракт слотов

Все значения строковые. Пять общих ключей `accountId`, `contract`, `address`, `authSuccess`, `addressSuccess` в `slots` должны совпадать у контроллера и обеих идентификаций. Остальной контракт принадлежит контроллеру; идентификация только очищает его поля через `resetSlots`. Если переименовать слот контроллера, обновить соответствующий ID и в `resetSlots` обеих идентификаций. Внутренние переменные сценария контроллер не копирует и не хранит.

| Ключ настройки | Слот по умолчанию | Назначение |
|---|---|---|
| `accountId` | `account_id` | GUID выбранного ЛС |
| `contract` | `account_number` | Номер ЛС |
| `address` | `account_address` | Адрес |
| `authSuccess` | `successful_identification` | Результат идентификации |
| `addressSuccess` | `address_success` | Подтвержденное частичное совпадение адреса |
| `service` | `current_service` | Услуга для реплики |
| `meterNumber` | `current_meter_number` | Полный номер ПУ |
| `meterNumberShort` | `current_meter_number_short` | Последние три символа номера |
| `meterLocation` | `current_meter_location` | Место установки, может быть пустым |
| `scaleName` | `current_scale_name` | Название шкалы |
| `previousReading` | `current_previous_reading` | Предыдущее показание |
| `digitsAfterDot` | `current_digits_after_dot` | Число дробных знаков |
| `scaleType` | `scale_type` | `"true"` при точности 0, иначе `"false"` |
| `newReading` | `current_new_reading` | Введенное значение; при успехе нормализовано с точкой |
| `error` | `reading_error` | Код ошибки значения |
| `status` | `reading_status` | `"ready"`, `"invalid"`, `"accepted"`; при завершении или неопределенности пусто |
| `skip` | `skip_service` | `"true"` - пропустить оставшиеся шкалы ПУ |
| `action` | `readings_action` | `init`, `process`, `next` |
| `stepId` | `readings_step_id` | Непрозрачный ID шага, вернуть агенту без изменений |
| `sentCount` | `readings_sent_count` | Число переданных шкал |
| `skippedCount` | `readings_skipped_count` | Число пропущенных шкал |

`reading_retry` отсутствует. Попытки исправления и сохранение их состояния реализуются в сценарии.

При переходах контроллер явно передает весь свой набор слотов. На новой шкале очищает ввод, ошибку, действие и пропуск. При ошибке значения сохраняет ту же шкалу и введенное значение, но обновляет `readings_step_id` для исправленного ввода. После успеха сохраняет данные отправленной шкалы до `next`.

## Действия, состояние и повторные вызовы

| Действие | Вход | Результат |
|---|---|---|
| `init` | `account_id`, `account_number`, `account_address`, стандартный `message.id` | Получение очереди, первая шкала или финальная статья |
| `process` | `account_id`, текущий `readings_step_id`, подтвержденный `current_new_reading` либо `skip_service = "true"` | Проверка/отправка, исправление или следующий прибор после пропуска |
| `next` | `account_id`, текущий `readings_step_id`; шкала уже передана | Следующая шкала или завершение |

Очередь, текущая позиция и статусы хранятся в `dialogStorage` контроллера; его область ограничена этим агентом и диалогом. SOAP-модуль работает в том же контексте.

Повторный `init` с тем же `message.id` не создает новую очередь; ID ранее начатых циклов сохраняются до конца диалога. Новый поиск ЛС и новый `init` с новым ID начинают независимый цикл. Для проверки повторной доставки на стенде сохранять исходный `message.id`.

Старый ID шага возвращает актуальное состояние без отправки/продвижения. Повторный `process` переданной шкалы возвращает ее успех без HTTP. `next` до успеха, пустой ID шага или несовпадающий ЛС ведут в техническую статью. Пропуск применяется до проверки значения и затрагивает только оставшиеся шкалы исходного прибора.

Защита рассчитана на последовательные вызовы. `dialogStorage.get/set` не предоставляет атомарного compare-and-set: при настройке цепочки исключить одновременное выполнение нескольких вызовов контроллера в одном диалоге.

## Проверка значений и ошибки

Принимается неотрицательное число с необязательной дробью через точку/запятую; пробелы по краям удаляются. Экспонента, текст после числа, минус и несколько разделителей отклоняются. Лишние дробные знаки, включая конечные нули, не округляются.

Сравнения и сложение выполняются по десятичным строкам без преобразования всего числа в `Number` и без `BigInt`. Одновременно проверяются: новое значение не меньше предыдущего, не больше предыдущего плюс `maxConsumption`, не больше максимума API. Границы допускаются. Предыдущая дробная часть не обрезается до точности нового ввода.

| Код | Причина |
|---|---|
| `"1"` | Меньше предыдущего |
| `"2"` | Превышен расход или максимум API |
| `"3"` | Некорректный формат |
| `"4"` | Лишние дробные знаки |

Поврежденные обязательные данные, отсутствие шкал у найденного прибора, некорректная точность, SOAP и ошибки хранения ведут в техническую статью. Пустой корректный ответ услуги означает отсутствие ее приборов.

Перед POST сохраняется `sending`. Только ответ `InputOfReadingsWithDotResult = 1` и сохранение результата дают `sent` / `accepted`. Явный отказ API или SOAP Fault сохраняется как `failed`, транспортный сбой или неразобранный ответ - как `unknown`. При ответе API 1 и сбое сохранения успеха в хранилище остается `sending`, сценарий получает техническую ошибку без успеха. Автоматических повторов POST нет. `sending`, `unknown`, `failed` при повторном входе продолжают вести в техническую статью.

При окончании очереди слоты текущего прибора очищаются, счетчики отражают шкалы, а не приборы. Пропуск всех приборов завершается без сообщения об успешной передаче.

## Локальные проверки

Из этого каталога:

```powershell
node --test ./readings.test.cjs
node --check ./readings-controller.js
node --check ./readings-soap-module.js
node --check ./identification_phone_number.js
node --check ./identification_account_number.js
```

Тесты используют `node:test`, синтетические данные, подмененные глобалы и HTTP-клиент; реальных запросов нет. По умолчанию XML-глобалы заменены снимками объектов. Если уже доступен `xml-js`, дополнительный прогон с `READINGS_XML_MODULES`, указывающим каталог существующих Node-пакетов, использует XML-строки через адаптер. Новые зависимости не устанавливаются. Наличие штатных `xml2js`, `js2xmlparser`, `https`, `axios` проверить на платформе.

Распознавание речи, сохранение попыток сценария при переходах и маршруты оператора проверяются на стенде по [scenario-plan.md](scenario-plan.md).
