# Развертывание приема показаний на проде

| Task | Entrypoint | Customer |
|---|---|---|
| Выкладка общей цепочки всех приборов и шкал | Входной маршрут нового приема показаний | СИГУРД |

План рассчитан на ручную настройку CraftTalk. Он не меняет платформу и не отправляет показания. Файлы берутся из этого каталога; подробные реплики - в [scenario-plan.md](scenario-plan.md), схема - в [scenario-flowchart.drawio](scenario-flowchart.drawio), контракт - в [readme.md](readme.md).

## 1. Зафиксировать прежнюю цепочку

1. Сохранить код, настройки и ID действующих агентов идентификации, четырех сценариев услуг, отправки и входного маршрута. Сохранить статьи и переходы, на которые потребуется вернуть вход при откате.
2. Новую цепочку создать отдельными экземплярами. Действующие агенты и статьи не перезаписывать: начатые диалоги должны завершаться на прежней цепочке.
3. Получить подтвержденный адрес продуктивного SOAP endpoint и проверить его доступность из среды JS-агента. REST URL другого API для этих агентов не подходит. Значения из локальных настроек сами по себе не подтверждают нужный контур.
4. Подготовить ЛС для проверки чтения и согласованной контрольной передачи. На стенде заранее пройти ошибки, пропуски, дробный голосовой ввод и повторные вызовы; локальные тесты не заменяют эти проверки.

## 2. Подготовить слоты

Создать отсутствующие слоты по таблице в README; существующие с подходящими ID использовать повторно. Идентификаторы должны точно совпасть в сценариях и настройках.

Особенно проверить:

- `current_meter_number_short` - последние три цифры номера для озвучивания, хранить текстом с сохранением начальных нулей;
- `account_id` - GUID, не номер ЛС;
- `current_new_reading` - строка с сохранением дроби, без преобразования только в целое число;
- `scale_type` - строки `"true"` / `"false"`;
- `readings_action`, `reading_status`, `reading_error` - технические метки;
- `readings_step_id` - полный ID шага без обрезки, перезаписи и самостоятельной генерации сценарием;
- счетчики `readings_sent_count`, `readings_skipped_count` относятся к шкалам.

В идентификации `slots` содержит только пять полей результата. `resetSlots` содержит ID очищаемых полей и пустые значения. Существующие старые слоты можно оставить для очистки; отсутствующие старые слоты специально не создавать и удалить из `resetSlots`. Поля нового цикла должны очищаться. Идентификацию и ее новые настройки переносить вместе.

## 3. Создать экземпляры агентов

| Новый объект | Исходник | Настройки | Особенность |
|---|---|---|---|
| SOAP-модуль | `readings-soap-module.js` | Использует настройки контроллера | Включить признак модуля |
| Контроллер | `readings-controller.js` | `readings-controller_settings.json` | Подключить SOAP-модуль |
| Идентификация по телефону | `identification_phone.js` | Соответствующий `_settings.json` | Новый экземпляр для новой цепочки |
| Идентификация по номеру | `identification_account.js` | Соответствующий `_settings.json` | Использовать также для другого ЛС |

Итого: три обычных JS-агента и один модуль. Записать фактические ID всех четырех объектов.

В SOAP-модуле включить «Является ли данный script модулем». В контроллере в поле «Подключаемые js-script модули» указать ID этого модуля. Модуль отдельно из сценария не вызывать. Все вызовы цикла должны попадать в один и тот же экземпляр контроллера: его `dialogStorage` привязан к агенту и диалогу.

`readings.test.cjs`, Markdown и draw.io не загружаются как JS-агенты. Старый `submit-readings.js` в новой цепочке не вызывается.

## 4. Создать статьи и заполнить настройки

Подготовить стартовый блок после идентификации и четыре статьи контроллера. Стартовый блок можно разместить в отдельной новой статье. При общем входе для успешного и пустого поиска различать `successful_identification`: только успешный результат с GUID разрешает `init`, неуспешный сохраняет прежний маршрут повторной идентификации/помощи.

| Компонент / поле | Что указать на проде |
|---|---|
| Контроллер: `url` | Подтвержденный продуктивный SOAP endpoint |
| Контроллер: `aiAgent` | ID экземпляра агента сценариев этого контура |
| Контроллер: `routingAgent` | Продуктивный резервный маршрут оператора |
| `articles.input` | symbolCode общей статьи приема и сообщения об успехе |
| `articles.correction` | symbolCode исправления |
| `articles.error` | symbolCode технической ошибки |
| `articles.finish` | symbolCode завершения ЛС |
| `timeoutMs` | Начальное значение 30000, согласованное с общим тайм-аутом выполнения JS-агента |
| `rejectUnauthorized` | По умолчанию `true`; проверить доверие сертификату SOAP сервера |
| `maxConsumption` | `"100"` согласно согласованному правилу |
| `services` | Порядок 24, 2, 21, 1 и названия услуг для реплик |
| Идентификация: `url` | Продуктивный SOAP endpoint |
| Идентификация: `aiAgent`, `routingAgent`, `operatorArticle` | Фактические маршруты прод-контура |
| Идентификация: `nextArticle` | Старт нового приема с веткой неуспешного поиска |
| Телефон: `phoneSlotId` | Слот фактического телефона канала |
| Телефон: `useHardcodedPhone` | `false` |
| Номер ЛС: `numberSlotId` | Слот введенного клиентом номера |

В контроллере должны быть заполнены все четыре статьи. В их полях используются symbolCode, а не заголовки статей. Вызовы агентов используют ID конкретного экземпляра, а не имя файла.

В идентификации входные `classifier` и `next_article` имеют приоритет над настройками. В новой входной ветке очистить их либо заполнить нужными прод-значениями. Иначе заполненный `nextArticle` может быть переопределен старым слотом и вернуть клиента в прежний сценарий.

## 5. Собрать переходы сценария

| Событие | Что сделать |
|---|---|
| Клиент согласился начать после идентификации | `readings_action = "init"`, очистить ввод/пропуск, вызвать контроллер |
| `reading_status = "ready"` | Озвучить услугу, прибор, шкалу и предыдущее показание; начать попытки новой шкалы |
| `scale_type = "true"` | Запросить целую часть |
| `scale_type = "false"` | Запросить значение с поддержкой дроби |
| Клиент подтвердил значение | `readings_action = "process"`, пропуск пустой, вызвать контроллер с текущим ID шага |
| Клиент не подтвердил число | Повторить ввод этой шкалы без вызова агента |
| Клиент отказался от прибора | `skip_service = "true"`, `readings_action = "process"`, вызвать контроллер с текущим ID шага |
| Контроллер вернул `accepted` | Озвучить успех этой шкалы, затем вызвать `next` с ее ID шага |
| Открыта статья исправления | Выбрать реплику по `reading_error`, вести одну повторную попытку внутри сценария; использовать обновленный ID шага |
| Открыта техническая статья | Помощь/оператор по действующим правилам; без автоматической отправки повторно |
| Открыта финальная статья | Итог по счетчикам; при согласии на другой ЛС вызвать новую идентификацию по номеру |

Не вызывать `next` до реплики об успехе и не вызывать `init` для перехода между шкалами. До вызовов `process` и `next` сохранять `account_id` и полученный `readings_step_id`. Внутреннее состояние попыток исправления должно переживать выход в JS-агент и возврат в статью; при исправлении оно не сбрасывается. Проверить это на стенде.

Контроллер вызывается последовательно: один ответ клиента - один вызов. Автоматические повторы и параллельные обработчики одного шага не включать.

## 6. Проверить изолированный вход на проде

До переключения общего потока организовать доступный сотрудникам вход к новой цепочке.

1. Пройти поиск по телефону и номеру ЛС, проверить выбранный GUID и адрес. Проверить ветку «ЛС не найден».
2. Выполнить `init`: сопоставить перечень приборов и шкал с учетной системой. Проверить услугу, последние три цифры номера, название шкалы, предыдущее значение, `scale_type`.
3. Проверить отказ от приборов и завершение без передачи: `init` и пропуски не вызывают `InputOfReadingsWithDot`.
4. Проверить голосовое дробное значение до подтверждения: сценарий должен повторить его без потери дробной части; ответ «нет» должен вернуть ввод той же шкалы.
5. На подготовленном ЛС выполнить согласованную контрольную передачу фактического показания. Убедиться в результате API 1, статусе `accepted`, верном приборе/шкале в реплике и отсутствии повторного POST на повторной доставке того же шага.
6. Проверить `next`, следующую шкалу, финал и другой ЛС. Ветку неизвестного результата и отказы API предварительно проверять на стенде; не создавать сетевые сбои на общем продуктивном потоке.

Контрольный `process` с корректным значением действительно записывает показание. Использовать данные согласованной проверки, а не произвольные числа. При неизвестном результате не повторять передачу для проверки; выяснить результат в учетной системе.

## 7. Переключить поток и наблюдать

1. Переключить вход новых обращений на новые экземпляры идентификации и старт нового сценария. Не переводить начатые старые циклы на новый контроллер: их состояние ему не принадлежит.
2. Прежние агенты, статьи и отправку оставить доступными для завершения старых диалогов и отката.
3. В первых новых диалогах проверить переходы по статьям, сохранение GUID/ID шага, распознавание дробей и реплики об успехе.
4. По логам контроллера и SOAP убедиться, что одна подтвержденная шкала вызывает одну запись, а успех появляется только после API 1. Технические ошибки и случаи `sending`/`unknown` передавать на проверку результата.
5. При повторных отправках, неверной привязке к шкале, потере дроби, сбросе попыток или неработающем техническом маршруте вернуть вход на прежнюю цепочку.

## 8. Откат

1. Вернуть сохраненный входной маршрут для новых обращений на старую цепочку.
2. Не удалять новые агенты, модуль, статьи и слоты, пока остаются начатые на них диалоги. Корректные новые циклы могут завершаться; проблемные направляются на помощь с проверкой уже выполненных передач.
3. Не очищать `dialogStorage` и не запускать `init` повторно ради восстановления неизвестной отправки. Результат сначала проверить в учетной системе.
4. Уже принятые API показания переключением сценария не отменяются. Их не передавать повторно через старую цепочку как способ отката.

Выкладка завершена, когда новая цепочка проверена по телефону и номеру, пройдены несколько приборов/шкал и дробный ввод, работает исправление и помощь, отсутствуют повторные записи и подтвержден путь отката.
