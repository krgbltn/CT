Итоговый план приема показаний по всем приборам учета

Реализовать один контроллер и общий сценарий, последовательно обрабатывающие все приборы и все их шкалы выбранного ЛС. Каждое подтвержденное показание проверяется и отправляется отдельно. После успешной отправки сценарий сообщает о принятии показания этой шкалы.

## План 1. Реализация агентов

### 1. Состав изменений

Рабочий каталог: `Sigurd/Агенты интеграций/Приборы учета/Прием показаний/Показания по всем счетчикам/`.

| Компонент | Назначение изменений |
|---|---|
| Обе копии агентов идентификации и их настройки | Передача GUID выбранного ЛС; исключение получения приборов |
| Новый `readings-controller.js` и настройки | Очередь, текущая шкала, проверки, отправка, переходы |
| Новый `readings-soap-module.js` | Получение приборов и отправка одного показания |
| `readme.md` | Подключение компонентов, настройки, слоты и последовательность вызовов |

Существующий `submit-readings.js` оставить, но исключить из новой цепочки.

Функции переиспользовать из существующих агентов. Новые зависимости не устанавливать. Каждый скрипт должен укладываться в ограничение 32 766 байт.

### 2. Агенты идентификации

Сохранить текущие правила поиска, выбора адреса и обработки ошибок.

После выбора ЛС передавать в сценарий:

- `account_id` — GUID из `ContractInfo.ID`;
- `account_number` — номер ЛС;
- `account_address` — адрес;
- существующие признаки результата идентификации.

Получение приборов и заполнение четырех фиксированных групп слотов из этих копий удалить. При новом поиске очищать предыдущие выходные данные ЛС и приборов.

После успешной идентификации сценарий запускает контроллер с действием `init`.

### 3. SOAP-модуль

На основе существующих функций выделить:

- запрос приборов `GetMDInfo_By_ContractIDAndNomenclatureCode`;
- отправку одного показания `InputOfReadingsWithDot`;
- формирование XML и разбор SOAP-ответов.

Получение приборов возвращает все `MDInfo` и все вложенные `MDScaleInfo`. Удаляются выбор первого прибора, первой шкалы и фильтры Гкал/м³.

Модуль подключается к контроллеру средствами платформы и не имеет самостоятельного запуска. Таким образом, работа с очередью и отправкой выполняется в контексте одного агента.

### 4. Очередь и хранение состояния

Контроллер получает приборы четырех услуг. Порядок по умолчанию:

1. Электроэнергия.
2. Горячая вода.
3. Холодная вода.
4. Отопление.

Порядок услуг задается настройками. Внутри услуги сохраняется порядок приборов и шкал API.

Очередь содержит уникальные `MDScaleID`. Повторный ID включается один раз: используется первая запись в заданном порядке услуг. Дополнительные правила обработки конфликтующих данных не вводятся.

Для записи сохраняются:

- услуга и принадлежность исходному прибору;
- полный номер и место установки;
- ID и название шкалы;
- предыдущие показания;
- допустимое количество дробных знаков;
- максимальное допустимое значение;
- подтвержденное новое значение;
- статус обработки.

Очередь и текущий шаг хранятся в `dialogStorage` контроллера. Принадлежность шкал прибору определяется по исходному `MDInfo`, а не только по серийному номеру.

Статусы записи: ожидает ввода, отправляется, передано, пропущено, ошибка отправки, результат неизвестен.

### 5. Контракт вызовов

| `readings_action` | Действие |
|---|---|
| `init` | Начать цикл выбранного ЛС и подготовить первую шкалу |
| `process` | Обработать пропуск либо проверить и отправить подтвержденное значение |
| `next` | После реплики об успехе подготовить следующую шкалу или завершить цикл |

Контроллер выдает `readings_step_id`. Сценарий сохраняет и возвращает его при вызове агента. Идентификатор связывает действие с конкретным шагом: повтор старого вызова не должен повторять отправку или применять прежнее значение к следующей шкале.

Повторная доставка одного вызова `init` не пересоздает уже начатый им цикл. Новый поиск и выбор ЛС запускают новый цикл.

При `skip_service = "true"` контроллер:

- обрабатывает пропуск раньше проверки значения;
- пропускает все оставшиеся шкалы текущего прибора;
- сохраняет результаты уже выполненных отправок;
- сбрасывает признак пропуска;
- подготавливает следующий прибор.

На новой шкале очищаются прежнее введенное значение, ошибка и метка действия.

### 6. Проверка показания

Все сравнения выполняются в JS:

- точка и запятая поддерживаются как десятичный разделитель;
- проверяется вся строка, без частичного разбора;
- учитывается `MDSDigitsAfterDot`;
- десятичные значения сравниваются точно, без молчаливого округления;
- новое значение должно быть не меньше предыдущего;
- расход должен быть не больше `100`;
- значение должно быть не больше максимума API.

Границы допускаются. Порог расхода задается настройкой, по умолчанию `100`.

В SOAP передается нормализованная строка с точкой. Отсутствующие обязательные данные шкалы не подменяются нулем и считаются технической ошибкой.

| `reading_error` | Причина |
|---|---|
| `"1"` | Новое показание меньше предыдущего |
| `"2"` | Превышен расход или максимум API |
| `"3"` | Некорректный формат |
| `"4"` | Превышена допустимая точность |

При ошибке значения контроллер не отправляет показание и не меняет текущую запись. Он сохраняет введенное значение, заполняет код ошибки и открывает статью исправления.

**Агент не считает попытки исправления. `reading_retry` в его контракте отсутствует.**

### 7. Отправка и технические ошибки

Последовательность отправки:

1. Сохранить значение и статус «отправляется».
2. Выполнить SOAP-запрос с настраиваемым тайм-аутом.
3. После ответа API `1` сохранить статус «передано».
4. Открыть общий сценарий с `reading_status = "accepted"` и данными отправленной шкалы.
5. Дождаться вызова `next` после реплики сценария.

До действия `next` слоты не переключаются на следующую шкалу.

При ошибке получения приборов, хранения состояния, SOAP-запроса или неизвестном результате отправки открывается настроенная техническая статья. Неопределенная отправка автоматически не повторяется.

Все входные точки завершаются через `resolve(ReplyMessage[])`, включая обработчики ошибок. Системные сообщения без предусмотренного действия не запускают отправку.

### 8. Слоты и настройки

Все значения слотов передаются строками.

| Слот | Назначение |
|---|---|
| `account_id` | GUID выбранного ЛС |
| `account_number`, `account_address` | Номер ЛС и адрес |
| `current_service` | Услуга в форме для подстановки в реплику |
| `current_meter_number` | Полный номер прибора |
| `current_meter_number_short` | Последние три символа номера для озвучивания |
| `current_meter_location` | Место установки |
| `current_scale_name` | Название шкалы |
| `current_previous_reading` | Предыдущее показание |
| `current_digits_after_dot` | Допустимое количество дробных знаков |
| `scale_type` | `"true"` при точности `0`; `"false"` при точности больше `0` |
| `current_new_reading` | Введенное показание |
| `reading_error` | Код ошибки значения |
| `reading_status` | `"ready"`, `"invalid"` или `"accepted"` |
| `skip_service` | Пропуск текущего прибора |
| `readings_action` | Действие контроллера |
| `readings_step_id` | Идентификатор шага |
| `readings_sent_count`, `readings_skipped_count` | Итоговые количества переданных и пропущенных шкал |

`current_service` заполняется из настроек: «электроэнергии», «горячей воды», «холодной воды», «отопления».

`scale_type` пересчитывается при подготовке каждой шкалы. Отсутствующая или некорректная точность — техническая ошибка.

Настройки также содержат URL, тайм-аут, ID агентов, порядок услуг, порог расхода, соответствие слотов и статьи приема, исправления, технической ошибки и завершения.

При переходах между агентом и сценарием нужный набор слотов передается явно. Произвольные внутренние данные сценария контроллер не хранит.

## План 2. Сценарий на платформе

Создать общий сценарий приема и статьи исправления, технической ошибки и завершения. Стартовый блок добавить после существующей успешной идентификации.

### 1. Старт приема

После идентификации и предусмотренных текущей цепочкой подтверждений адреса:

> Я буду называть последние три цифры номера прибора учета и предыдущие показания. Пожалуйста, передавайте показания по названному прибору. Начнем? Скажите «да» или «нет».

- **Да:** установить `readings_action = "init"` и вызвать контроллер.
- **Нет:** перейти к предложению другого ЛС без отправки.

Вводная реплика произносится один раз на цикл ЛС.

### 2. Озвучивание текущей шкалы

При входе с `reading_status = "ready"`:

> По прибору учета {current_service}, номер {current_meter_number_short}, шкала {current_scale_name}, последние показания {current_previous_reading}. Готовы назвать текущее показание?

- **Да:** перейти к вводу.
- **Нет:** установить `skip_service = "true"`, `readings_action = "process"` и вызвать контроллер с текущим `readings_step_id`.

Пропуск относится к текущему прибору и всем его оставшимся шкалам.

### 3. Ввод и подтверждение

| `scale_type` | Реплика |
|---|---|
| `"true"` | «Назовите целую часть показания до запятой» |
| `"false"` | «Назовите показание прибора учета. Для дробной части скажите “запятая” в нужном месте» |

Результат записывается в строковый слот `current_new_reading`. При дробном вводе необходимо сохранить дробную часть.

Затем:

> Вы назвали показание {current_new_reading}, верно? Скажите «да» или «нет».

- **Да:** установить `readings_action = "process"` и вызвать контроллер с текущим `readings_step_id`.
- **Нет:** очистить значение и повторить ввод той же шкалы.

Отрицательное подтверждение не означает пропуск прибора.

### 4. Успешная отправка

При входе с `reading_status = "accepted"`:

> Показание по прибору учета {current_service}, номер {current_meter_number_short}, шкала {current_scale_name}, принято.

После реплики установить `readings_action = "next"` и вызвать контроллер с текущим `readings_step_id`.

Сообщение об успехе произносится после каждой успешной отправки шкалы. Для многотарифного прибора оно не означает, что остальные шкалы уже переданы.

### 5. Исправление значения

Контроллер открывает статью с `reading_status = "invalid"`, кодом ошибки и прежними данными шкалы.

| Код | Содержание сообщения |
|---|---|
| `"1"` | Значение меньше предыдущего; назвать предыдущее показание |
| `"2"` | Превышен допустимый расход или предел |
| `"3"` | Не удалось распознать корректное число |
| `"4"` | Превышено допустимое количество дробных знаков |

После сообщения:

> Хотите изменить показание? Скажите «да» или «нет».

- **Да:** повторить ввод по `scale_type`, подтвердить значение и вызвать контроллер с действием `process`.
- **Нет:** перейти в предусмотренный схемой маршрут помощи или оператора.

По схеме разрешается одна повторная попытка после ошибки. Повторная подтвержденная ошибка ведет в маршрут помощи, независимо от смены кода ошибки.

Количество попыток и сохранение состояния исправления реализуются средствами сценария. Контроллеру счетчик не передается. При переходе к новой шкале сценарий начинает обработку попыток заново.

### 6. Техническая ошибка

Реплика:

> Не удалось подтвердить передачу показаний. Потребуется помощь специалиста.

Далее используются существующие правила перевода на оператора и его доступности.

Эта статья не запускает автоматическую повторную отправку и не сообщает об успехе.

### 7. Завершение ЛС

Финальная статья открывается после окончания очереди, включая отсутствие приборов или пропуск всех приборов.

По итоговым счетчикам различаются успешная передача, частичная передача и отсутствие переданных показаний. При нулевом числе отправок сообщение об успешной передаче не произносится.

Затем:

> Хотите передать показания по другому лицевому счету? Скажите «да» или «нет».

- **Да:** запросить номер ЛС и вызвать агент идентификации по номеру; после выбора ЛС начать новый цикл.
- **Нет:** завершить диалог по существующей схеме.

## Проверки и подключение

### Изолированные проверки агентов

С подмененным HTTP-клиентом проверить:

- несколько приборов одной услуги, несколько шкал прибора и повторные `MDScaleID`;
- отсутствие приборов и отдельных услуг;
- точку, запятую, ноль, некорректный формат и лишнюю точность;
- равенство предыдущему значению, расход ровно `100`, равенство максимуму и превышение границ;
- изменение точности `0 → 3 → 0` и `scale_type`: `"true" → "false" → "true"`;
- исправление той же шкалы и пропуск оставшихся шкал прибора;
- повторные `init`, `process` и `next` без повторной отправки и лишнего продвижения;
- ошибки SOAP, хранения и неопределенный результат отправки;
- сохранение данных отправленной шкалы до действия `next`;
- переход к другому ЛС.

### Проверки сценария на стенде

Проверить сохранение дробной части, подтверждение «нет», работу одной повторной попытки без агентного счетчика, корректные данные в реплике об успехе, пропуск всех приборов и новый цикл другого ЛС.

Сначала подключить модуль, контроллер и статьи на тестовом контуре. После прохождения проверок переключить входную цепочку с четырех прежних сценариев на общий сценарий. Реальные SOAP-вызовы не использовать для локальной проверки кода.
