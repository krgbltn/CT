# Настройка сценария приема показаний

| Task | Entrypoint | Customer |
|---|---|---|
| Общий сценарий всех приборов и шкал | Старт после идентификации; статьи `input`, `correction`, `error`, `finish` | СИГУРД |

Это инструкция настройки, а не выгрузка статей: файл сам не изменяет платформу. Фактические ID экземпляров агентов и symbolCode статей задать при подключении.

Блок-схема: [Mermaid](scenario-flowchart.md) или [редактируемый draw.io, два листа](scenario-flowchart.drawio).

## Подготовка

1. Создать слоты по [контракту](readme.md#контракт-слотов). `current_new_reading` хранит число строкой без потери дробной части; `scale_type` сравнивается со строками `"true"` / `"false"`.
2. Создать четыре статьи: общий прием (`articles.input`), исправление (`articles.correction`), техническая ошибка (`articles.error`), завершение (`articles.finish`). Записать их symbolCode в настройки контроллера.
3. Вызовы направлять на фактический ID контроллера. Передавать действие, ЛС, полученный ID шага и значение/пропуск.
4. Контроллер открывает статьи через `/switchredirect`, явно заполняя свои слоты. Состояние попыток сохранять средствами сценария, без передачи счетчика агенту; проверить его сохранение через эти переходы на стенде.
5. Сохранить существующие ветки неуспешной идентификации и помощи/оператора. Исключить прежний `submit-readings.js` и параллельные вызовы контроллера по одному диалогу.

## 1. Старт после идентификации

После предусмотренных текущей цепочкой подтверждений адреса открыть старт только при `successful_identification = "true"` и заполненном `account_id`.

Один раз на выбранный ЛС:

> Я буду называть последние три цифры номера прибора учета и предыдущие показания. Пожалуйста, передавайте показания по названному прибору. Начнем? Скажите «да» или «нет».

- **Да:** очистить `skip_service` и `current_new_reading`, установить `readings_action = "init"`, вызвать контроллер.
- **Нет:** без вызова контроллера нейтрально предложить другой ЛС либо завершить диалог. Не использовать счетчики прошлого цикла для итоговой реплики.

Контроллер возвращает первую шкалу или сразу финальную статью при пустой очереди.

## 2. Общая статья: выбор ветки

| `reading_status` | Ветка |
|---|---|
| `"ready"` | Озвучить текущую шкалу и запросить готовность |
| `"accepted"` | Сообщить об успехе этой шкалы и вызвать `next` |

Ошибки значения контроллер направляет сразу в исправление, технические - в статью ошибки. Пустой или неизвестный статус не означает успех.

## 3. Готовность и пропуск

На новой шкале начать новый цикл попыток средствами сценария.

> По прибору учета {current_service}, номер {current_meter_number_short}, шкала {current_scale_name}, последние показания {current_previous_reading}. Готовы назвать текущее показание?

`current_service` уже содержит нужную форму, например «электроэнергии». Название шкалы произносить также для тарифов одного прибора. Место установки можно добавить только при заполненном `current_meter_location`.

- **Да:** очистить `skip_service`, перейти к вводу.
- **Нет:** установить `skip_service = "true"`, `readings_action = "process"`, вызвать контроллер с текущим `readings_step_id`.

Отказ пропускает все еще не переданные шкалы прибора. Другие приборы услуги остаются в очереди; ранее отправленные шкалы сохраняют успех.

## 4. Ввод и подтверждение

Числовые сравнения в сценарии не выполнять.

| `scale_type` | Реплика |
|---|---|
| `"true"` | «Назовите целую часть показания до запятой» |
| `"false"` | «Назовите показание прибора учета. Для дробной части скажите “запятая” в нужном месте» |

Записать результат в `current_new_reading`, сохранив дробную часть. Затем:

> Вы назвали показание {current_new_reading}, верно? Скажите «да» или «нет».

- **Да:** убедиться, что `skip_service` пустой, установить `readings_action = "process"`, вызвать контроллер с текущим ID шага.
- **Нет:** очистить значение и повторить ввод той же шкалы без вызова контроллера.

Отрицательное подтверждение не является пропуском и не считается проверенной агентом ошибкой. До подтверждения отправки нет.

## 5. Успешная передача

При `reading_status = "accepted"`:

> Показание по прибору учета {current_service}, номер {current_meter_number_short}, шкала {current_scale_name}, принято.

После реплики установить `readings_action = "next"`, вызвать контроллер с тем же ID шага. Слоты еще относятся к отправленной шкале; следующая появится только после этого вызова.

Сообщение произносится после каждой отправленной шкалы. У многотарифного прибора после «День» отдельно запрашивается и передается «Ночь». До `accepted` об успехе не сообщать.

## 6. Исправление

Статья получает `reading_status = "invalid"`, код ошибки, введенное значение и прежние данные шкалы. Для следующего вызова использовать обновленный ID шага из ответа.

| Код | Реплика |
|---|---|
| `"1"` | «Новое показание меньше предыдущего и не может быть принято. Предыдущее показание {current_previous_reading}. Хотите изменить показание?» |
| `"2"` | «Новое показание превышает допустимый расход или предел и не может быть принято. Предыдущее показание {current_previous_reading}. Хотите изменить показание?» |
| `"3"` | «Не удалось распознать корректное число. Хотите повторить показание?» |
| `"4"` | «Указано больше дробных знаков, чем допускает шкала. Допустимое количество: {current_digits_after_dot}. Хотите изменить показание?» |

При первой подтвержденной ошибке:

- **Да:** использовать единственную повторную попытку сценария; очистить значение, повторить ввод по `scale_type`, подтвердить и вызвать `process` с обновленным ID шага.
- **Нет:** существующий маршрут помощи/оператора по схеме.

После повторной подтвержденной ошибки, даже с другим кодом, перейти в маршрут помощи. Счетчик и состояние исправления существуют только в сценарии: агент их не получает, не увеличивает и не возвращает. Не перезапускать ветку новой шкалы `ready` ради исправления.

## 7. Техническая ошибка

> Не удалось подтвердить передачу показаний. Потребуется помощь специалиста.

Далее - действующая ветка помощи/оператора с проверкой доступности. Не вызывать автоматически `process`, `next`, `init` и не говорить об успехе. Часть прошлых шкал могла быть передана; результат текущей операции проверяется специалистом.

## 8. Завершение ЛС

Слоты текущего прибора очищены; счетчики относятся к шкалам, а не приборам.

| Условие | Смысл итоговой реплики |
|---|---|
| Переданных шкал больше 0, пропусков нет | Показания переданы |
| Оба счетчика больше 0 | Часть шкал передана, часть пропущена |
| Переданных 0, есть пропуски | Передачи не было; приборы пропущены |
| Оба счетчика 0 | Доступных шкал не найдено |

Затем:

> Хотите передать показания по другому лицевому счету? Скажите «да» или «нет».

- **Да:** запросить номер ЛС, вызвать обновленную идентификацию по номеру, после выбора повторить старт приема.
- **Нет:** существующее завершение диалога.

## Приемка на стенде

Проверить несколько приборов услуги и тарифы прибора; сохранение дроби при слове «запятая»; отрицательное подтверждение; одну повторную попытку через переходы между агентами; отказ исправлять; пропуск после частичной передачи и отказ от всех приборов; ошибку API; правильные услугу/номер/шкалу в сообщении об успехе; другой ЛС. Системные сообщения не должны отправлять показания, повтор шага - отправлять их дважды.
