# Прием показаний приборов учета

Набор JS-агентов для поиска лицевых счетов, получения информации о приборах учета и передачи введенных показаний в SOAP API СИГУРД.

| Task | Entrypoint | Customer |
|---|---|---|
| Поиск ЛС по телефону | `identification_phone_number.js` | СИГУРД |
| Поиск ЛС по номеру | `identification_account_number.js` | СИГУРД |
| Передача показаний | `submit-readings.js` | СИГУРД |

## Агенты

### identification_phone_number

Файлы: `identification_phone_number.js`, `identification_phone_number_settings.json`.

Ищет лицевые счета по телефону вызовом `GetContractsInfo_By_Phone`. Для выбранного ЛС запрашивает приборы вызовом `GetMDInfo_By_ContractIDAndNomenclatureCode`: `1` для отопления, `2` для ГВС, `21` для ХВС и `24` для электроэнергии.

По умолчанию телефон берется из слота `sys_phone`. Для тестирования можно установить `useHardcodedPhone: true` и задать номер в `hardcodedPhone`.

При корректном пустом результате поиска агент возвращает диалог в статью из `next_article` с fallback на `nextArticle`, передавая `successful_identification: "false"`. Переход выполняется к агенту из `classifier` с fallback на `aiAgent`. Прежние слоты ЛС, адреса и приборов очищаются, `address_success` передаётся пустым; дальнейший шаг определяет сценарий статьи.

При неуспешном выборе адреса, ошибке запроса, некорректном SOAP/XML или повреждённых данных агент переводит диалог в `operatorArticle`, передавая `successful_identification: "false"`. Если `operatorArticle` не задана, используется `routingAgent`.

### identification_account_number

Файлы: `identification_account_number.js`, `identification_account_number_settings.json`.

Ищет ЛС по цифровой части номера из слота `account_number_client` (настройка `numberSlotId`) вызовом `FindAllByContractNumber`. Дальнейшая обработка приборов и ошибок идентична агенту поиска по телефону.

### submit-readings

Файлы: `submit-readings.js`, `submit-readings_settings.json`.

Получает введенные значения из слотов `readings_*` и отправляет каждую заполненную пару «GUID шкалы - показание» вызовом `InputOfReadingsWithDot`. Передача считается успешной только при значении `InputOfReadingsWithDotResult = 1`.

При ошибке SOAP-запроса, неверном ответе или неполной паре слотов агент направляет диалог к ID из настройки `routingAgent`.

При `debug: true` агент не вызывает API и не выполняет переходы. Вместо этого выводит в чат полные XML-запросы `InputOfReadingsWithDot`, подготовленные для каждой передачи.

## Последовательность сценария

1. `identification_phone_number` ищет ЛС по телефону, а `identification_account_number` — по введённому номеру ЛС. Каждый новый поиск выполняется независимо от предыдущего результата.
2. При нескольких разных адресах агент выполняет адресную идентификацию, описанную ниже. Список кандидатов хранится в собственном `dialogStorage` только до выбора адреса. Единственный найденный адрес выбирается сразу. Если ЛС не найдены, агент возвращается в следующую статью с `successful_identification: "false"`.
3. Для выбранного ЛС агент передает в сценарий номер ЛС, исходный адрес, номера приборов, предыдущие показания и GUID одной шкалы на услугу. Для отопления выбирается шкала `Гкал`, для ГВС — шкала `м3`; для ХВС и электроэнергии используется первая шкала первого прибора в ответе. Все остальные кандидаты удаляются.
4. Сценарий запрашивает новые показания в слотах `readings_*` и запускает `submit-readings`.
5. Агент отправки передает заполненные показания.
6. После успешной передачи агент направляет диалог к ID из слота `classifier` с fallback на `aiAgent`; целевая статья берется из `next_article` с fallback на `nextArticle`. Сценарий статьи спрашивает клиента, хочет ли он передать показания по другому ЛС; при согласии запрашивает номер ЛС и запускает `identification_account_number`.
7. При согласии передать показания по другому адресу выполняется новый поиск по введённому номеру ЛС. Если он вернул несколько адресов, идентификация повторяется.

Автоматического обхода найденных ЛС нет: оба агента поиска передают `has_next_account: "false"` и очищают `readings_lookup_agent`.

### Адресная идентификация

1. Агент спрашивает: «Назовите адрес, по которому Вы обращаетесь». Сопоставляет населённый пункт, улицу/микрорайон/квартал и номер дома. Единственное полное совпадение завершает идентификацию; названные клиентом квартира, корпус и строение не должны противоречить найденному адресу.
2. Если полного совпадения нет, по той же реплике определяется наиболее подходящий адрес. При единственном лучшем частичном совпадении агент спрашивает: «Вы обращаетесь по адресу …? Скажите “да” или “нет”», называя населённый пункт. «Да» завершает идентификацию и заполняет `address_success: "true"`, «нет» переводит к списку. При непонятном ответе вопрос повторяется один раз, затем также выводится список.
3. При отсутствии совпадений, равнозначных кандидатах или отказе от предложенного адреса агент перечисляет уникальные адреса нумерованным списком. Номер можно назвать цифрами или словами. «Нет» означает перевод на оператора. Некорректный номер уточняется один раз; повторная ошибка переводит на оператора.

Каждый ответ агента содержит ровно один `ReplyMessage`: вопрос, список или команду перехода. Повторный вход обрабатывает текущее состояние до нового запроса SOAP. Системные сообщения подтверждаются через `makeAckReply`.

Используются правила общей идентификации с учётом числительных и небольших ошибок распознавания речи. Населённый пункт берётся из `ContractInfo.City`, а при его отсутствии — из `ContractInfo.Adress`. Он учитывается при полном и частичном сопоставлении, озвучивается в вопросе подтверждения и списке. Город, уже указанный в адресе, не дублируется. Поддержаны SOAP-адреса без префикса «г.», обозначения `кв-л`, `квл`, `квартал`. Начальный почтовый индекс не озвучивается. Одинаковые адреса объединяются с учётом населённого пункта; при нескольких ЛС по одному адресу используется первый из ответа API.

Техническое состояние хранится в `dialogStorage.readings_identification`. После выбора, пустого результата поиска или перевода на оператора оно удаляется вместе с прежними ключами `contracts`, `contracts_addresses`, `contracts_pagination`. Результат остаётся в слотах только выбранного ЛС. Ошибки SOAP/XML, повреждённое состояние и отсутствие обязательных данных у найденных ЛС направляют диалог к оператору; старые слоты приборов и шкал очищаются.

## Слоты

| Назначение | Слот |
|---|---|
| Идентифицированный ЛС | `account_number` |
| Адрес выбранного ЛС из `ContractInfo.Adress` | `account_address` |
| Успех идентификации | `successful_identification` |
| Подтверждено частичное совпадение адреса | `address_success` |
| Номер ПУ электроэнергии | `number_electricity_meter` |
| Предыдущее / новое показание электроэнергии | `recent_electricity` / `readings_electricity` |
| GUID шкалы электроэнергии | `scale_id_electricity` |
| Номер ПУ ГВС | `number_hot_water` |
| Предыдущее / новое показание ГВС | `recent_hot_water` / `readings_hot_water` |
| GUID шкалы ГВС | `scale_id_hot_water` |
| Номер ПУ ХВС | `number_cold_water` |
| Предыдущее / новое показание ХВС | `recent_cold_water` / `readings_cold_water` |
| GUID шкалы ХВС | `scale_id_cold_water` |
| Номер ПУ отопления | `number_heating` |
| Предыдущее / новое показание отопления | `recent_heating` / `readings_heating` |
| GUID шкалы отопления | `scale_id_heating` |
| Наличие следующего ЛС — всегда `false` | `has_next_account` |
| Прежний агент возврата — очищается | `readings_lookup_agent` |

Слоты `scale_electricity`, `scale_hot_water`, `scale_cold_water`, `scale_heating` используются сценарием как признаки шкалы. Для SOAP-передачи нужны отдельные технические слоты `scale_id_*`.

Оба агента поиска передают исходный адрес выбранного ЛС в слот из настройки `slots.address` (по умолчанию `account_address`). Во время уточняющих вопросов и при неуспешной идентификации слот очищается. Для вопросов и списка адресов агент самостоятельно формирует сокращённый текст без почтового индекса.

Слот из настройки `slots.addressSuccess` (по умолчанию `address_success`) получает строку `"true"` только после положительного ответа клиента на подтверждение частично совпавшего адреса и успешного завершения идентификации. При полном совпадении, автоматическом выборе единственного адреса, выборе номера из списка, уточняющих вопросах и ошибках передаётся пустая строка `""`. Каждый новый поиск очищает прежнее значение.

## Настройки агентов поиска

- `operatorArticle` — статья перевода на оператора. Значение вынесено из прежнего кода в оба файла настроек.
- `routingAgent` — агент перевода на оператора, если статья не задана.
- `aiAgent` / слот `classifier` — ИИ-агент для переходов к статьям; слот имеет приоритет.
- `nextArticle` / слот `next_article` — статья после успешной идентификации или корректного пустого результата поиска; слот имеет приоритет.
- `numberSlotId` — слот цифровой части номера ЛС, по умолчанию `account_number_client`.
- `phoneSlotId` — слот телефона, по умолчанию `sys_phone`.
- `slots` — существующие выходные слоты результата идентификации и приборов. Дополнительные слоты состояния не требуются.
- `slots.addressSuccess` — слот подтверждённого частичного совпадения адреса, по умолчанию `address_success`.

## Настройки submit-readings

- `aiAgent` - ID агента ИИ, по умолчанию `ai_pribor`.
- `routingAgent` - ID агента маршрутизации ошибок, по умолчанию `routingagent`.
- `nextArticle` - финальная статья после успешной передачи показаний по последнему ЛС.
- `debug` - при `true` отправка отключена, подготовленные данные выводятся в чат.
- `continueNextAccount` — прежняя настройка автоматического возврата. С текущими агентами поиска возврат не выполняется, поскольку `has_next_account` всегда `false`. Для другого адреса сценарий запрашивает номер ЛС.

## SOAP API

- `GetContractsInfo_By_Phone` - поиск ЛС по телефону.
- `FindAllByContractNumber` - поиск ЛС по цифровой части номера.
- `GetMDInfo_By_ContractIDAndNomenclatureCode` - получение прибора и шкалы.
- `InputOfReadingsWithDot` - передача нового показания.

Описание методов: `API/SOAP/`.
