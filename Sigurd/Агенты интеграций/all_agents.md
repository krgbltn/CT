# Агенты интеграций 

## Как читать описание

- **ЛС** — лицевой счёт; **ПУ** — прибор учёта; **ЛК** — личный кабинет; **ЭЭ** — электроэнергия; **ГВС/ХВС** — горячее/холодное водоснабжение.
- Большинство агентов работают с ЛС, уже выбранным при идентификации клиента. В запросах `{uid}` обозначает внутренний идентификатор этого ЛС.
- Результаты проверки и полученные данные передаются в сценарий обслуживания. Сценарий использует их, чтобы озвучить ответ, задать следующий вопрос или продолжить обслуживание. `final_answer` — слот с кодом результата проверки; его значение имеет смысл только в рамках конкретного агента.
- Для большинства агентов «перевод на оператора» означает переход в настроенный сценарий перевода. У агентов приёма показаний особенности маршрутизации указаны отдельно.
- Отсутствие искомых данных может быть штатным результатом, а не причиной перевода. Такие случаи перечислены в вариантах выхода каждого агента.

В блоках «Входные данные» перечислены слоты, заполненные в сценарии и используемые для запросов к API или выбора нужной услуги и прибора в полученных данных.

## 1. Дистанционные сервисы

### **`check_lk_registration`** — Проверка регистрации в личном кабинете

**Назначение.** Определить, зарегистрирован ли владелец выбранного ЛС в личном кабинете.

**Входные данные.** `uid` — внутренний идентификатор выбранного ЛС, полученный при идентификации; необходим для запроса карточки ЛС.

**Запрос и данные.** По идентификатору ЛС выполняется `GET /{uid}/info`. Из карточки ЛС берётся признак регистрации владельца в ЛК.

**Варианты выхода.** В сценарий передаются признак регистрации `is_owner_registered` и значение слота `final_answer`:
- `final_answer = 1` — владелец зарегистрирован: в ответе `GET /{uid}/info` поле `account.is_owner_registered` равно `true`;
- `final_answer = 2` — регистрация владельца не подтверждена: поле `account.is_owner_registered` равно `false`, отсутствует либо имеет другое значение, отличное от `true`.

**Перевод на оператора.** При ошибке запроса, отсутствии ответа или другой ошибке выполнения. Отсутствие регистрации само по себе к переводу не приводит.

## 2. Договорная работа

### **`info_by_user_id`** — Проверка статуса лицевого счёта и типа дома

**Назначение.** Уточнить статус найденного ЛС и тип дома для продолжения договорного сценария.

**Входные данные.** Обязательный слот `uid` — внутренний идентификатор ЛС, полученный при идентификации или поиске ЛС.

**Запросы и данные.** Выполняются `GET /{uid}/info` для получения статуса ЛС из поля `status` и `GET /{uid}/disconnection_report_info` для определения типа дома из поля `housetype`: многоквартирный, частный или иной. Значение `final_answer` выбирается только по `status`; тип дома на него не влияет.

**Варианты выхода.** В сценарий передаются тип дома, если он получен, и значение слота `final_answer`:
- `final_answer = 1` — ЛС действует: в ответе `GET /{uid}/info` поле `status` равно `"Действует"`;
- `final_answer = 2` — ЛС выключен: поле `status` равно `"Выключен"`;
- `final_answer = 3` — ЛС закрыт или ликвидирован: поле `status` равно `"Закрыт"` или `"Ликвидирован"`;
- `final_answer = 4` — поле `status` содержит любое другое значение либо отсутствует в полученном ответе.

**Перевод на оператора.** Если не передан идентификатор ЛС, не удалось получить его карточку или возникла другая ошибка выполнения. Если не удалось получить только тип дома, агент продолжает сценарий с результатом проверки статуса, без типа дома.

## 3. Идентификация общая

### **`identification`** — Идентификация клиента по телефону и адресу

**Назначение.** Найти ЛС, связанные с телефоном клиента, и определить, по какому адресу он обращается. Общий агент используется в разных сценариях, в том числе при отключениях ТСН.

**Входные данные.** `phone` — номер телефона клиента, передаваемый в запросе поиска ЛС.

**Запросы и данные.** Выполняется `GET /contracts_by_phone` с номером телефона. Сервис возвращает список ЛС с идентификаторами, номерами и адресами. После выбора ЛС дополнительно запрашиваются:
- `GET /{uid}/info` — статус ЛС и город;
- `GET /{uid}/disconnection_report_info` — тип дома.

По полному адресу также определяются населённый пункт из настроенного справочника и телефон ЕДДС, если для территории есть соответствие.

**Логика и варианты выхода.**
1. **Найден один ЛС.** - сохраняет сведения о ЛС и продолжает сценарий. 
2. **Найдено несколько ЛС.** Агент просит назвать адрес и сопоставляет ответ с адресами из сервиса. Для выбора нужны совпадения населённого пункта, улицы и основного номера дома; в названиях допускаются небольшие ошибки распознавания. Квартира не обязательна. Если подходят несколько записей, выбирается первая; дополнительное подтверждение не запрашивается.
3. **ЛС выбран.** В сценарий передаются его идентификатор, номер и адрес, а также полученные дополнительные сведения. Ошибки получения статуса, города или типа дома не отменяют успешный выбор ЛС: соответствующие дополнительные данные просто не передаются.
4. **ЛС не найдены, некорректный ответ или ошибка.**
   - **Запрос `GET /contracts_by_phone` завершился ошибкой** — агент сразу направляет диалог на оператора, без возврата `final_answer = error`.
   - **Запрос выполнен, но ответ отсутствует, не является массивом или содержит пустой массив** — в сценарий возвращается `final_answer = error`; дальнейшее действие определяется сценарием.
   


**Перевод на оператора.** Агент непосредственно запускает сценарий перевода, если:
- произошла ошибка запроса поиска ЛС по телефону;
- при нескольких ЛС не удалось сопоставить названный адрес;
- при продолжении диалога утрачены данные найденных ЛС либо выбранная запись отсутствует.

## 4. Начисления

### **`get_service_amount_to_pay`** — Сумма к оплате по выбранной услуге

**Назначение.** Определить сумму задолженности по услуге, которую назвал клиент: электроэнергии, ХВС, ГВС или отоплению.

**Входные данные.** Обязательные слоты:
- `uid` — внутренний идентификатор выбранного ЛС, полученный при идентификации;
- `service_type` — выбранная услуга: `Электроэнергия`, `Холодное водоснабжение`, `Горячее водоснабжение` или `Отопление`. Сценарий должен привести слова клиента к одному из этих значений; по нему агент выбирает допустимые названия услуги в ответе API.

**Запрос и данные.** Выполняется `GET /{uid}/transactions`. Из массива `transactions` выбираются все строки, у которых поле `service_name` соответствует нужной услуге с учётом вариантов её названия. Для них суммируются значения поля `debt`.

**Варианты выхода.** Передаются название услуги, сумма к оплате и значение слота `final_answer`:
- `final_answer = 1` — сумма `debt` по всем выбранным строкам больше нуля; эта сумма передаётся в слот `amount_to_pay`;
- `final_answer = 2` — сумма `debt` по выбранным строкам равна нулю или меньше нуля: задолженности нет либо имеется переплата; `amount_to_pay = 0`.

**Перевод на оператора.** Если не выбран ЛС, услуга не задана или не распознана, в ответе нет подходящих операций, запрос завершился ошибкой либо ответ отсутствует.

### **`get_total_debt`** — Общая задолженность по лицевому счёту

**Назначение.** Определить общую сумму к оплате по ЛС.

**Входные данные.** Обязательный слот `uid` — внутренний идентификатор выбранного ЛС. Услугу или прибор указывать не требуется.

**Запрос и данные.** Выполняется `GET /{uid}/info`; из поля `account.balance` берётся общее сальдо ЛС.

**Варианты выхода.** В сценарий передаётся значение слота `final_answer`:
- `final_answer = 1` — значение `account.balance` после преобразования в число больше нуля: есть задолженность; передаются сальдо и сумма к оплате;
- `final_answer = 2` — значение `account.balance` после преобразования в число равно нулю или меньше нуля: долга нет либо есть переплата; `amount_to_pay = 0`;
- `final_answer = 3` — поле `account.balance` отсутствует в ответе или равно `null`. Это отдельный результат для сценария, без непосредственного перевода агентом.

**Перевод на оператора.** Если не выбран ЛС, запрос завершился ошибкой, ответ отсутствует либо полученное сальдо нельзя преобразовать в число.

### **`check_water_devices`** — Проверка возможности передачи показаний воды

**Назначение.** Проверить, есть ли по ЛС хотя бы один прибор ГВС или ХВС, по которому можно принять показания.

**Входные данные.** Обязательный слот `uid` — внутренний идентификатор выбранного ЛС. ГВС и ХВС проверяются автоматически; выбирать услугу или прибор не требуется.

**Запрос и данные.** Выполняется `GET /{uid}/info`. Из массива `account.devices` выбираются приборы ГВС и ХВС по полю `service_name` с учётом вариантов названий услуг. Для определения ГВС дополнительно учитывается `is_hot_water = true`. Затем проверяются поля разрешения приёма показаний у выбранных приборов.

**Варианты выхода.** В сценарий передаётся значение слота `final_answer`:
- `final_answer = 1` — среди выбранных водяных приборов есть хотя бы один с `accepts_readings = true` или `readings_accept_type = "allowed"` без учёта регистра;
- `final_answer = 2` — в `account.devices` нет подходящих водяных приборов либо ни у одного из них не выполнено ни одно из двух условий разрешения приёма показаний. Отсутствующий или некорректный список приборов также обрабатывается как отсутствие приборов.

Проверка не определяет статус самих услуг ГВС и ХВС.

**Перевод на оператора.** Если не выбран ЛС, запрос завершился ошибкой, ответ отсутствует или произошла другая ошибка выполнения. Отсутствие подходящего прибора возвращается как `final_answer = 2`.

### **`check_service_debt`** — Задолженность по наименованию услуги

**Назначение.** Получить сумму к оплате по уже известному сценарию наименованию услуги.

**Входные данные.** Обязательные слоты:
- `uid` — внутренний идентификатор выбранного ЛС;
- `service_name` — название искомой услуги. Оно используется для поиска в поле `transactions[].service_name`: название из ответа API должно содержать переданное значение с учётом регистра. Слот `service_type` этот агент не использует.

**Запрос и данные.** Выполняется `GET /{uid}/transactions`. Агент находит первую строку, наименование которой содержит переданное название услуги, и берёт задолженность из этой строки. В отличие от `get_service_amount_to_pay`, все подходящие строки не суммируются.

**Варианты выхода.** В сценарий передаются название услуги в слоте `service_name` и сумма к оплате в слоте `amount_to_pay`: положительная задолженность либо ноль, если задолженность нулевая или отрицательная. Слот `final_answer` не устанавливается.

**Перевод на оператора.** Если не выбран ЛС, не передано название услуги, подходящая строка не найдена, запрос завершился ошибкой либо ответ отсутствует.


### **`check_email_doc`** — Проверка доставки документов на электронную почту

**Назначение.** Проверить, подключена ли электронная доставка документов и к какой группе относится адрес получателя.

**Входные данные.** Обязательный слот `uid` — внутренний идентификатор выбранного ЛС. Адрес электронной почты заранее передавать не нужно: он получается из карточки ЛС.

**Запрос и данные.** Выполняется `GET /{uid}/info`. Из ответа берутся признак электронной доставки `email_doc` и адрес электронной почты `email`.

**Варианты выхода.** В сценарий передаётся значение слота `final_answer`:
- `final_answer = 1` — поле `email_doc` равно `true`, а строка `email` заканчивается на `.ru`: доставка включена на адрес в зоне `.ru`;
- `final_answer = 2` — поле `email_doc` равно `true`, но `email` не указан, пуст или не заканчивается на `.ru`: доставка включена, адрес относится к другой группе;
- `final_answer = 3` — поле `email_doc` равно `false`, отсутствует либо имеет другое значение, отличное от `true`: включение доставки не подтверждено.

**Перевод на оператора.** Если не выбран ЛС, запрос завершился ошибкой, ответ отсутствует либо произошла другая ошибка выполнения.

## 5. Отключение ЭЭ

### **`disabling_electro`** — Проверка отключения электроэнергии

**Назначение.** Узнать, зарегистрировано ли отключение электроэнергии по ЛС и имеется ли задолженность.

**Входные данные.** `uid` — внутренний идентификатор выбранного ЛС, полученный при идентификации; необходим для запроса отключений.

**Запрос и данные.** Выполняется `GET /{uid}/disconnections_electro`. Сервис возвращает сведения об отключении или наряде, текст сообщения, тип отключения, вид работ, признак задолженности и тип дома.

**Варианты выхода.** Полученные сведения передаются в сценарий вместе со значением слота `final_answer`:
- `final_answer = 1` — в ответе `GET /{uid}/disconnections_electro` присутствует объект `disconnection`: есть сведения об отключении или наряде. Значение `debt` при выборе этой ветки не учитывается;
- `final_answer = 2` — объект `disconnection` отсутствует или равен `null`, а признак `debt` установлен (`true`): отключения нет, но есть задолженность;
- `final_answer = 3` — объект `disconnection` отсутствует или равен `null`, а признак `debt` не установлен (`false` или отсутствует): нет сведений ни об отключении, ни о задолженности.

**Перевод на оператора.** При ошибке запроса, отсутствии ответа или другой ошибке выполнения. Наличие долга либо отсутствие зарегистрированного отключения сами по себе не вызывают перевод: агент возвращает соответствующую ветку сценария.

### **`ksrt_report`** — Оформление аварийной заявки в КСРТ

**Назначение.** Передать заявку по проблеме с электроснабжением: отсутствие ЭЭ, неисправность пульта, частые отключения, мигание света, отсутствие фазы, низкое напряжение или другая причина.

**Входные данные.** Для формирования заявки используются слоты:
- `uid` — внутренний идентификатор выбранного ЛС;
- `phone` — контактный телефон клиента, передаваемый в заявке;
- `message` — код причины: `NoPower` — нет электроэнергии, `Invalid` — неисправность пульта, `FrequentShutdowns` — частые отключения, `Other` — другая причина, `LightFlashes` — мигает свет, `NoPhase` — отсутствует фаза, `LowVoltage` — низкое напряжение. Необязателен: при отсутствии используется `NoPower`;
- `comment` — комментарий клиента. Необязателен: при отсутствии используется комментарий «Отсутствует ЭЭ» из настроек.

Признак `is_building` не берётся из входного слота: в настройках он всегда равен `true`.

**Запрос и данные.** Выполняется `POST /{uid}/disconnection_report_info`. Передаются причина обращения, комментарий клиента и контактный телефон. Заявка всегда оформляется с признаком проблемы во всём доме или у соседей; если причина не задана, используется «отсутствие электроэнергии».

**Варианты выхода.** Значение слота `final_answer = 1` — заявка передана — устанавливается, если `POST /{uid}/disconnection_report_info` завершился без ошибки и вернул непустое тело ответа. Отдельное поле статуса заявки агент не проверяет, номер заявки не возвращает. В README ожидаемым ответом сервиса указан `200 OK` с пустым телом, однако текущая реализация пустое тело ответа направляет в ветку перевода на оператора.

**Перевод на оператора.** При ошибке отправки заявки, пустом ответе сервиса или другой ошибке выполнения.

## 6. Отключения ТСН

В этой папке находятся три агента. Упомянутая в её README идентификация выполняется общим агентом `identification` из папки «Идентификация общая» и описана в разделе 3.

### **`disabling_tsn`** — Проверка отключения ГВС или теплоснабжения

**Назначение.** Проверить наличие отключения ГВС/теплоснабжения и задолженности по ЛС.

**Входные данные.** `uid` — внутренний идентификатор выбранного ЛС, полученный при идентификации; необходим для запроса отключений.

**Запрос и данные.** Выполняется `GET /{uid}/disconnections_heat`. Получаются описание отключения, вид работ, полные сведения об отключении, признак задолженности и тип дома. Полные сведения сохраняются для дальнейшего сценария, в том числе для подготовки обращения об отсутствии уведомления.

**Варианты выхода.** В сценарий передаётся значение слота `final_answer`:
- `final_answer = 1` — в ответе `GET /{uid}/disconnections_heat` присутствует объект `disconnection`: отключение зарегистрировано. Значение `debt` при выборе этой ветки не учитывается;
- `final_answer = 2` — объект `disconnection` отсутствует или равен `null`, а признак `debt` установлен (`true`): отключение не зарегистрировано, но есть задолженность;
- `final_answer = 3` — объект `disconnection` отсутствует или равен `null`, а признак `debt` не установлен (`false` или отсутствует): нет сведений ни об отключении, ни о задолженности.

**Перевод на оператора.** При ошибке запроса, отсутствии ответа или другой ошибке выполнения. Штатные значения слота `final_answer` от `1` до `3` возвращаются в сценарий для дальнейшей обработки.

### **`disabling_tsn_plan`** — Проверка срока окончания работ

**Назначение.** Определить, наступил ли заявленный срок окончания работ по отключению ГВС/теплоснабжения.

**Входные данные.** `uid` — внутренний идентификатор выбранного ЛС. Дату окончания работ заранее передавать не нужно: агент получает её повторным запросом к API.

**Запрос и данные.** Выполняется `GET /{uid}/disconnections_heat`. Из объекта `disconnection` берутся описание `text` и дата со временем окончания работ `date_end`; срок сравнивается с текущим моментом.

**Варианты выхода.** В сценарий передаются сведения об отключении и значение слота `final_answer`:
- `final_answer = 1` — объект `disconnection` и поле `disconnection.date_end` получены, текущий момент равен дате и времени из `date_end` или позже них: срок окончания уже наступил или прошёл. По логике сценария требуется передача оператору для уточнения ситуации;
- `final_answer = 2` — объект `disconnection` и поле `disconnection.date_end` получены, текущий момент раньше даты и времени из `date_end`: срок ещё не наступил. Сценарий может сообщить клиенту ожидаемую дату окончания;
- `final_answer = 3` — объект `disconnection` отсутствует или равен `null` либо поле `disconnection.date_end` не заполнено.

**Перевод на оператора.** При ошибке запроса, отсутствии ответа или другой ошибке выполнения агент запускает перевод непосредственно. При `final_answer = 1` он возвращается в сценарий, который должен выполнить перевод по бизнес-условию «срок работ истёк».

## 7. Приборы учета

### **`check_service_device`** — Проверка наличия и активности услуги и прибора

**Назначение.** По выбранной услуге отдельно проверить наличие услуги, подтверждение её активности, наличие прибора и возможность приёма показаний.

**Входные данные.** Обязательные слоты:
- `uid` — внутренний идентификатор выбранного ЛС;
- `service_type` — услуга: `Электроэнергия`, `Холодное водоснабжение`, `Горячее водоснабжение` или `Отопление`. Значение заранее определяется сценарием по обращению клиента.

Слот `device` не требуется: приборы нужной услуги агент находит сам.

**Запросы и данные.** Выполняется `GET /{uid}/info`. Наличие услуги проверяется по списку услуг именно выбранного ЛС, приборы ищутся по названию услуги. Если прибор найден, выполняется дополнительный `GET /{uid}/disconnection_report_info` для получения типа дома.

**Варианты выхода.** Слот `final_answer` не устанавливается. В сценарий передаются четыре слота со значениями `true`/`false`:
- `service_exists` — услуга есть в списке услуг ЛС;
- `service_active` — активность услуги подтверждена: услуга найдена и хотя бы у одного её прибора есть признак активной услуги;
- `device_exists` — найден хотя бы один прибор этой услуги;
- `device_active` — хотя бы по одному такому прибору разрешён приём показаний.

Дополнительно передаются доступные сведения об услуге, городе, типе дома и режиме приёма показаний. Если признака активности услуги нет, её активность считается неподтверждённой; это не доказывает отключение услуги. Запрет приёма показаний также сам по себе не означает снятие прибора с расчётов.

**Перевод на оператора.** Если не выбран ЛС, услуга не задана или неизвестна, ответ сервиса неполный/неподходящего формата либо любой из выполняемых запросов завершился ошибкой. Если данные корректны, отсутствие услуги или прибора возвращается обычными признаками «нет».

### **`check_service_device_active`** — Проверка услуги и прибора по разрешению приёма показаний

**Назначение.** Проверить наличие услуги и прибора по упрощённому правилу: услуга считается имеющейся, если для неё найден прибор; действующими услуга и прибор считаются при разрешённом режиме приёма показаний.

**Входные данные.** Обязательные слоты:
- `uid` — внутренний идентификатор выбранного ЛС;
- `service_type` — услуга: `Электроэнергия`, `Холодное водоснабжение`, `Горячее водоснабжение` или `Отопление`.

Слот `device` не требуется: приборы нужной услуги агент находит сам.

**Запросы и данные.** Выполняется `GET /{uid}/info`. Приборы выбираются по названию услуги. Для оценки действующности используется режим приёма показаний `ALLOWED`. Если прибор найден, дополнительно выполняется `GET /{uid}/disconnection_report_info` для получения типа дома.

**Варианты выхода.** Слот `final_answer` не устанавливается. В сценарий передаются четыре слота со значениями `true`/`false`:
- `service_exists` и `device_exists` — оба равны `true`, если найден хотя бы один подходящий прибор; иначе `false`;
- `service_active` и `device_active` — оба равны `true`, если у хотя бы одного подходящего прибора режим приёма показаний `ALLOWED`; иначе `false`.

Дополнительно передаются доступные сведения о городе, типе дома и режиме приёма показаний. В отличие от предыдущего агента, отдельный список услуг ЛС не проверяется.

**Перевод на оператора.** Если не выбран ЛС, услуга не задана или неизвестна, ответ сервиса имеет неподходящий формат либо любой из выполняемых запросов завершился ошибкой. Отсутствие прибора — штатный результат с признаками «нет».

### **`check_housetype`** — Определение типа дома

**Назначение.** Определить, относится ли ЛС к многоквартирному, частному или иному дому.

**Входные данные.** Обязательный слот `uid` — внутренний идентификатор выбранного ЛС.

**Запрос и данные.** Выполняется `GET /{uid}/disconnection_report_info`; из ответа берётся тип дома.

**Варианты выхода.** В сценарий передаётся значение слота `final_answer`:
- `final_answer = 1` — в ответе `GET /{uid}/disconnection_report_info` заполнено поле `housetype`; его значение дополнительно передаётся в одноимённый слот `housetype`;
- `final_answer = 2` — поле `housetype` отсутствует, равно `null` или содержит пустое значение.

**Перевод на оператора.** Если не выбран ЛС, запрос завершился ошибкой, ответ отсутствует либо возникла другая ошибка выполнения. Отсутствие самого поля типа дома возвращается как `final_answer = 2`.

### **`device_verification_check`** — Получение даты следующей поверки

**Назначение.** Получить дату следующей поверки прибора по выбранной услуге.

**Входные данные.** Обязательные слоты:
- `uid` — внутренний идентификатор выбранного ЛС;
- `service_type` — услуга: `Электроэнергия`, `Холодное водоснабжение`, `Горячее водоснабжение` или `Отопление`.

Слот `device` не требуется: используется первый найденный прибор выбранной услуги.

**Запрос и данные.** Выполняется `GET /{uid}/info`. Агент выбирает первый прибор нужной услуги и берёт дату его следующей поверки. Предварительно выбирать конкретный прибор не требуется.

**Варианты выхода.** В сценарий передаётся значение слота `final_answer`:
- `final_answer = 1` — в массиве `account.devices` из ответа `GET /{uid}/info` найден прибор с подходящим `service_name`, и у первого такого прибора заполнено поле `next_check`; дата передаётся в слот `next_check`;
- `final_answer = 2` — подходящий прибор в `account.devices` не найден либо у первого подходящего прибора поле `next_check` отсутствует, равно `null` или пусто. Отсутствующий или некорректный список приборов также обрабатывается как отсутствие прибора.

Агент не сравнивает дату с текущим днём и не определяет, просрочена ли поверка.

**Перевод на оператора.** Если не выбран ЛС, услуга не задана или неизвестна, запрос завершился ошибкой, ответ отсутствует либо возникла другая ошибка выполнения.

### **`last_reading_get`** — Получение последнего показания по услуге

**Назначение.** Получить последнее сохранённое показание прибора для выбранной услуги.

**Входные данные.** Обязательные слоты:
- `uid` — внутренний идентификатор выбранного ЛС;
- `service_type` — название услуги или его часть для поиска в `service_name` прибора. В этом агенте используется прямое сравнение с учётом регистра, без справочника вариантов названия услуги.

Слот `device` заранее не требуется: агент сам находит прибор и возвращает его идентификатор.

**Запрос и данные.** Выполняется `GET /{uid}/devices`. Из списка выбирается первый прибор, название услуги которого содержит переданное значение. У него берётся первая запись из набора последних показаний.

**Варианты выхода.** При успехе в сценарий передаются идентификатор прибора в слоте `device`, значение показания в `last_reading` и его дата в `last_reading_date`. Слот `final_answer` не устанавливается.

**Перевод на оператора.** Если не выбран ЛС, не указана услуга, подходящий прибор или последнее показание не найдены, необходимые данные показания неполны, запрос завершился ошибкой либо ответ отсутствует.

### **`get_all_last_readings`** — Получение последних показаний по всем приборам

**Назначение.** Получить последние показания всех приборов выбранного ЛС, без уточнения услуги или конкретного прибора у клиента.

**Входные данные.** Обязательный слот `uid` — внутренний идентификатор выбранного ЛС. Слоты `service_type` и `device` не требуются.

**Запрос и данные.** Выполняется `GET /{uid}/devices`. Для каждого прибора берутся его номер, услуга и только первая запись из набора последних показаний. Показание учитывается, если есть и значение, и дата; ноль считается допустимым значением.

**Варианты выхода.** В сценарий передаются список приборов с показаниями и значение слота `final_answer`:
- `final_answer = 1` — в массиве из ответа `GET /{uid}/devices` есть хотя бы один прибор, у которого запись `last_reading.readings[0]` содержит и `value`, и непустую `date`. Значение `value = 0` учитывается; отсутствующее значение, `null` или пустая строка не учитываются. Дополнительно формируется текст для озвучивания с номерами приборов, значениями и датами;
- `final_answer = 2` — ответ `GET /{uid}/devices` представляет собой пустой массив: приборов по ЛС нет;
- `final_answer = 3` — массив приборов непустой, но ни у одного прибора запись `last_reading.readings[0]` не содержит одновременно допустимого `value` и непустой `date`.

Приборы без показаний сохраняются в общем списке, но не включаются в текст для клиента. Последующий вопрос и обработка ответа клиента выполняются сценарием. Дата трактуется как дата передачи показания, без утверждения, кто его внёс.

**Перевод на оператора.** Если не выбран ЛС, запрос завершился ошибкой либо вместо списка приборов получен ответ неподходящего формата. Значения `final_answer = 2` и `final_answer = 3` возвращаются в сценарий без непосредственного перевода.

### 7.1. Прием показаний

Эти агенты используют SOAP-сервис СИГУРД. Общая последовательность: поиск ЛС → получение приборов и предыдущих показаний → ввод клиентом новых показаний в сценарии → передача показаний в СИГУРД.

#### **`identification_phone_number`** — Поиск лицевого счёта по телефону для приёма показаний

**Назначение.** Найти ЛС по телефону звонящего и подготовить данные для ввода показаний.

**Входные данные.** `sys_phone` — телефон звонящего, передаваемый в запросе поиска ЛС.

**Запросы и данные.** Метод `GetContractsInfo_By_Phone` возвращает связанные с телефоном ЛС, их номера, внутренние идентификаторы и адреса. Для текущего ЛС вызывается `GetMDInfo_By_ContractIDAndNomenclatureCode` по четырём услугам: отоплению, ГВС, ХВС и электроэнергии.

По каждой доступной услуге передаются номер прибора, предыдущее показание и данные одной шкалы для отправки нового показания. Для отопления выбирается шкала «Гкал», для ГВС — «м3»; для ХВС и электроэнергии — первая шкала первого прибора в ответе. Также передаются номер и адрес текущего ЛС и признак наличия следующего ЛС.

**Варианты выхода.** Результат идентификации передаётся в слоте `successful_identification`; слот `final_answer` не устанавливается.
- **ЛС найден:** в сценарий возвращаются `successful_identification = true` и доступные сведения о приборах. Сам агент новые показания не запрашивает и не отправляет.
- **ЛС по телефону не найден:** возвращается `successful_identification = false`. Дальнейший сценарий должен предложить поиск по номеру ЛС через `identification_account_number`. Ошибка запроса поиска, после которой нет данных для обработки, также может попасть в эту ветку.
- **Найдено несколько ЛС:** текущим становится первый; остальные сохраняются для возможной последовательной обработки. При повторном вызове агент может перейти к следующему сохранённому ЛС.

Отсутствие сведений по отдельному прибору не отменяет найденный ЛС: в сценарий передаются только доступные данные.

**Перевод на оператора.** Предусмотрен переход в статью обработки ошибок/перевода, если телефон отсутствует или возникла ошибка, попавшая в общий обработчик. Штатный результат «ЛС не найден» возвращается в сценарий для поиска по номеру, без непосредственного перевода.

#### **`identification_account_number`** — Поиск лицевого счёта по номеру для приёма показаний

**Назначение.** Найти ЛС по названному клиентом номеру, если поиск по телефону не дал результата или клиент хочет передать показания по другому ЛС.

**Входные данные.** `account_number_client` — цифровая часть номера ЛС, введённая клиентом в сценарии и передаваемая в запросе поиска ЛС.

**Запросы и данные.** Вызывается `FindAllByContractNumber` с цифровой частью номера ЛС. Для найденного ЛС выполняются запросы `GetMDInfo_By_ContractIDAndNomenclatureCode` по отоплению, ГВС, ХВС и электроэнергии. Выбор приборов и шкал такой же, как при поиске по телефону.

**Варианты выхода.** Результат идентификации передаётся в слоте `successful_identification`; слот `final_answer` не устанавливается.
- **ЛС найден:** в сценарий передаются `successful_identification = true`, номер и адрес ЛС, доступные номера приборов, предыдущие показания и данные шкал.
- **ЛС не найден:** передаётся `successful_identification = false`; дальнейшее действие определяется сценарием. Отсутствие данных после ошибки запроса поиска также может дать этот результат.
- **Найдено несколько ЛС:** обрабатывается текущий, передаётся признак наличия следующего; предусмотрена последовательная обработка сохранённого списка.

**Перевод на оператора.** Предусмотрен переход в статью обработки ошибок/перевода, если номер ЛС не передан или возникла ошибка, попавшая в общий обработчик. Отсутствие найденного ЛС само по себе возвращается в сценарий как неуспешная идентификация.

#### **`submit-readings`** — Передача новых показаний

**Назначение.** Отправить в СИГУРД показания, которые клиент уже ввёл в сценарии.

**Входные данные.** Для каждой передаваемой услуги нужна полная пара слотов:

| Услуга | Идентификатор шкалы из агента поиска | Новое показание от клиента |
|---|---|---|
| Электроэнергия | `scale_id_electricity` | `readings_electricity` |
| ГВС | `scale_id_hot_water` | `readings_hot_water` |
| ХВС | `scale_id_cold_water` | `readings_cold_water` |
| Отопление | `scale_id_heating` | `readings_heating` |

Обязательна хотя бы одна полная пара; каждое показание должно быть числом. Для услуг, по которым передача не выполняется, оба слота пары должны быть пустыми. Предыдущие показания и заводские номера приборов для отправки не используются.

**Запрос и данные.** Для каждой заполненной пары «идентификатор шкалы — новое показание» вызывается `InputOfReadingsWithDot`. Могут передаваться показания электроэнергии, ГВС, ХВС и отопления. Сервис возвращает результат приёма; успешным считается только значение `1` для каждой отправки.

**Варианты выхода.** Слот `final_answer` не устанавливается; дальнейший переход определяется успешностью передачи показаний и настройками обработки следующих ЛС.
- **Все показания приняты:** агент возвращает диалог в сценарий продолжения. По умолчанию сценарий предлагает передать показания по другому ЛС; при согласии запрашивает его номер и запускает поиск по номеру ЛС.
- **Включена автоматическая обработка следующих ЛС:** после успешной отправки агент возвращается к агенту поиска, пока в сохранённом списке есть следующий ЛС.
- **Включён отладочный режим:** запросы не отправляются; в чат выводятся подготовленные данные для проверки.

**Перевод на оператора.** Агент обращается к настроенному агенту маршрутизации, если:
- нет ни одной полной пары «шкала — показание»;
- есть шкала без показания или показание без шкалы;
- показание не является числом;
- запрос завершился ошибкой, ответ не удалось разобрать или сервис вернул результат, отличный от `1`, хотя бы для одной отправки;
- требуется автоматический переход к следующему ЛС, но не указан агент возврата.

## 8. Проверка сетевой организации

### **`check_network_organization`** — Определение обслуживающей сетевой организации

**Назначение.** Узнать, какая сетевая организация обслуживает выбранный ЛС, для дальнейшей маршрутизации обращения.

**Входные данные.** `uid` — внутренний идентификатор выбранного ЛС; используется в URL запроса согласно текущим настройкам агента.

**Запрос и данные.** Выполняется `GET /{uid}/network_organization_data`. Сервис возвращает идентификатор, название организации и доступные контакты. В сценарий агент передаёт идентификатор организации.

**Варианты выхода.** Сценарий продолжается с полученным значением слота `network_organization_id`:
- `network_organization_id = 1` — ИЭСК, включая её территориальные подразделения;
- `network_organization_id = 2` — БЭСК;
- `network_organization_id = 3` — ОГУЭП «Облкоммунэнерго»;
- `network_organization_id = 4` — другая организация / нет нужного источника.

Отдельный `final_answer` не устанавливается. Значение «другая организация» само по себе не вызывает перевод агентом. Если ответ получен, но идентификатор в нём отсутствует, текущая реализация продолжает сценарий без заполнения этого значения.

**Перевод на оператора.** При ошибке запроса, отсутствии ответа или другой ошибке выполнения.

## 9. Юридические лица

### **`find_account_by_inn`** — Поиск лицевого счёта юридического лица по ИНН

**Назначение.** Найти организацию и её ЛС по ИНН клиента.

**Входные данные.** Обязательный слот `inn` — ИНН организации, сообщённый клиентом в сценарии и передаваемый в запросе поиска абонента.

**Запрос и данные.** Выполняется `GET /abonents_by_inn` в сервисе юридических лиц с переданным ИНН. Ответ содержит сведения об абоненте, признак регистрации в ЛК и список его договоров с номерами ЛС. Для результата используется первый абонент и первый непустой номер ЛС в его списке.

**Варианты выхода.** В сценарий передаётся значение слота `final_answer`:
- `final_answer = 1` — ответ `GET /abonents_by_inn` содержит непустой массив абонентов, и в массиве `WebProperties` первого абонента есть хотя бы одна запись с непустым `ContractNo`. Первый найденный номер передаётся в слот `ur_account_number`;
- `final_answer = 2` — массив абонентов пуст или ответ не является массивом; либо у первого абонента нет массива `WebProperties`, он пуст или ни одна его запись не содержит непустого `ContractNo`.

Агент не предлагает выбрать между несколькими найденными ЛС.

**Перевод на оператора.** Если ИНН отсутствует, запрос завершился ошибкой, тело ответа отсутствует либо возникла другая ошибка выполнения. Полученный пустой список — штатный результат `final_answer = 2`, без непосредственного перевода.

### **`autodial_search`** — Проверка звонка о задолженности в базе автодозвона

**Назначение.** Проверить, был ли клиенту-юрлицу успешный автодозвон о задолженности за последние несколько суток, и получить связанный с ним ЛС.

**Входные данные.** Обязательный слот `phone_ul` — телефон юридического лица, передаваемый в запросе поиска в базе автодозвона.

**Запрос и данные.** Выполняется `GET /api/kc/debt-call` в сервисе автообзвона контакт-центра с телефоном юридического лица и признаком поиска только по юрлицам. Период в запросе не задаётся; используется период сервиса по умолчанию — 3 суток. Ответ содержит признак найденного дозвона, связанный номер ЛС и дополнительные сведения о звонке. Агент использует признак дозвона и номер ЛС.

**Варианты выхода.** В сценарий передаётся значение слота `final_answer`:
- `final_answer = 1` — в ответе `GET /api/kc/debt-call` поле `debt_call.exists` равно `true`: сервис подтвердил успешный дозвон. Номер ЛС из поля `ls` передаётся в слот `autodial_ls`; заполненность `ls` на выбор `final_answer` не влияет;
- `final_answer = 2` — объект `debt_call` отсутствует либо его поле `exists` равно `false`, отсутствует или имеет другое значение, отличное от `true`: успешный дозвон не подтверждён.

**Перевод на оператора.** Если телефон юридического лица отсутствует, сервис не ответил, запрос завершился ошибкой, в том числе ошибкой доступа, либо истёк таймаут запроса — 3 секунды.
