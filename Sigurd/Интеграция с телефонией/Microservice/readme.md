### Описание и структура

Агенты связывают канал CraftTalk с микросервисом телефонии: входящий агент пересылает сообщения в канал, исходящий преобразует сообщения платформы в события для микросервиса.

| Файл | Назначение |
|------|------------|
| `incoming_sigurd-webhook.js` | Входящий JS-агент: пересылает объект `message` в `integration_channel` без преобразований. |
| `outgoing_sigurd-webhook.js` | Исходящий обработчик канала: читает `message.data`, отправляет события `reply`, `end`, `operator_connected` в микросервис. |
| `outgoing_sigurd-webhook_settings.json` | Пример настроек исходящего агента, включая соответствие тематик группам `routingTopics`. |
| `channel_settings.json` | Пример настроек канала: проект и идентификатор исходящего агента. |
| `readme.md` | Логика обработки, контракт сообщений и порядок подключения. |

JSON-файлы служат примерами конфигурации. Скрипты не загружают их с диска: настройки агентов читаются из глобального объекта `agentSettings`, настройки канала задаются в платформе.

### Варианты подключения

**Вариант 1: Напрямую через канал (integration_channel)**

Микросервис шлёт сообщения напрямую в канал платформы (`PLATFORM_WEBHOOK_URL`). Входящий jsagent не участвует. Outgoing-скрипт ловит ответ бота из канала и отправляет webhook обратно в микросервис.

```
Телефония → sigurd-service → POST в integration_channel → платформа/бот → outgoing-скрипт → webhook → sigurd-service
```

**Вариант 2: Через агента (jsagent)**

Микросервис шлёт сообщения на URL входящего jsagent (`AGENT_URL`). Входящий скрипт форвардит сообщение в канал. Outgoing-скрипт ловит ответ бота и отправляет webhook обратно в микросервис.

```
Телефония → sigurd-service → POST в incoming jsagent → incoming форвардит в канал → платформа/бот → outgoing-скрипт → webhook → sigurd-service
```

### Логика входящего агента

Последовательность вызовов: `main()` → `sendMessage(message)` → HTTP POST в канал.

1. `main()` логирует входящий объект `message`.
2. `sendMessage()` отправляет весь объект на `agentSettings.incoming_api` без изменения полей.
3. В запросе используются заголовки `Authorization` (значение `authorization_token_incoming`) и `Content-Type: application/json`.
4. Ошибка HTTP-запроса логируется внутри `sendMessage()` и не пробрасывается дальше. Повторная отправка не реализована; явный таймаут не задан.
5. После выполнения `main()` вызывается `resolve(response)`.

**Особенность текущей реализации:** `sendMessage()` возвращает `{}`, но `main()` не возвращает этот результат. Поэтому при обычном завершении, в том числе после перехваченной ошибки HTTP, вызывается `resolve(undefined)`. Внешний `.catch()` при других ошибках вызывает `resolve({})`.

| Настройка | Использование |
|-----------|---------------|
| `incoming_api` | Полный URL webhook канала. В коде есть резервный пример `http://opbot-channels:8082/webhooks/integration_channel/channel_35328b3`; для окружения нужно задать свой адрес. |
| `authorization_token_incoming` | Значение заголовка `Authorization`, по умолчанию пустая строка. |

### Логика исходящего агента

Последовательность вызовов: `main()` → `handleMessage()` → `sendWebhook(payload)`. Для события подключения оператора дополнительно вызывается `finishDialog()`.

#### Входные данные и слоты

Агент читает сообщение платформы из `message.data`:

- тип сообщения — `message.data.message_type`;
- текст — `message.data.content.text`, при отсутствии используется `""`;
- слоты — `message.data.slots`, при отсутствии используется `[]`.

Слоты ожидаются в формате `[{ "id": "имя_слота", "value": "значение" }]`. `getSlotValue()` берёт первое совпадение по `id`; при отсутствии слота или его значения возвращает `""`.

| Слот | Назначение |
|------|------------|
| `call_id_sigurd` | Идентификатор звонка, включается в каждый webhook. Без непустого значения агент логирует ошибку и прекращает обработку. |
| `session_id_sigurd` | Идентификатор сессии, включается в каждый webhook. При отсутствии передаётся `""`. |
| `sys_omniuserid` | Используется для поиска и завершения диалога CraftTalk после события подключения оператора. |
| `theme` | Тематика для выбора групп при `message_type === 18`. |
| `operator_name` | Резервный источник имени оператора. |
| `DialogFinishReason` | Значение `finishdialog` переводит сообщение типа `1` в событие завершения. |

#### Обработка типов сообщений

| `message_type` | Условие | Событие / действие |
|----------------|---------|--------------------|
| `1` | Есть хотя бы один признак завершения, описанный ниже | `end`, текст не передаётся. |
| `1` | Признаков завершения нет | `reply` с текстом из `content.text`. |
| `16` | Всегда | `end`. |
| `18` | Всегда | `operator_connected` с именем оператора, тематикой и группами; затем попытка завершения диалога CraftTalk. |
| Остальные | Всегда | Только запись в лог, webhook не отправляется. |

Для типа `1` достаточно любого из условий:

- текст точно равен `Диалог завершен`;
- `String(meta.force_finish_message_sent ?? "").toLowerCase() === "true"`;
- значение слота `DialogFinishReason` точно равно `finishdialog`.

Объект `meta` выбирается как `msg.meta || msg.content.meta || {}`: если `msg.meta` присутствует и является truthy, метаданные из `content.meta` не используются.

#### Подключение оператора и выбор группы

При типе `18` имя оператора берётся из первого непустого источника:

1. `msg.operator.fname` и `msg.operator.lname`, объединённые через пробел;
2. `msg.context.first_operator_name`;
3. слот `operator_name`;
4. `null`, если имя не найдено.

Тематика берётся **только из слота `theme`**. Группы выбираются так:

```js
const topic = getSlotValue(slots, "theme") || null
const topicInfo = (ROUTING_TOPICS || {})[topic]
    || (ROUTING_TOPICS || {})["Не определена"]
const groups = topicInfo?.groups || []
```

Значение `theme` должно точно совпадать с **ключом** в `agentSettings.routingTopics`, включая регистр и пробелы. Вложенное поле `routingTopics[ключ].topic` в этой обработке не читается. В webhook `target.topic` передаётся исходное значение слота, либо `null`.

Например, при `theme = "Отключение ЭЭ"` и конфиге из `outgoing_sigurd-webhook_settings.json` передаётся группа **301 — «Отключение ЭЭ»**:

```json
{
  "target": {
    "topic": "Отключение ЭЭ",
    "groups": [{ "id": 301, "name": "Отключение ЭЭ" }]
  }
}
```

Если тема отсутствует или ключ не найден, используется запись `"Не определена"` — в текущем примере это **411 — «Разное»**. При этом `target.topic` остаётся исходной темой или `null`, а не заменяется на `"Не определена"`. Если резервной записи тоже нет либо у выбранной записи отсутствует `groups`, передаётся `[]`. Пустой массив `groups` у найденной темы сохраняется: например, `"Магелан"` из текущего конфига не переводится на резервную группу.

**Граница ответственности:** этот агент не вызывает `routingagent` и не задаёт очередь распределения внутри CraftTalk. На событии подключения оператора он сообщает микросервису телефонную цель в `target.groups`. Применение этой цели выполняется на стороне микросервиса/телефонии; маршрутизация диалога к оператору внутри CraftTalk определяется отдельно сценарием и настройками платформы.

В коде есть функция `getRoutingInfo(text)`, извлекающая тему из текста `/switchredirect routingagent ...`, но она нигде не вызывается. Её резервная группа `411` не участвует в действующей обработке: фактический fallback берётся из `routingTopics["Не определена"]`.

#### Завершение диалога после подключения оператора

После отправки `operator_connected` вызывается `finishDialog(omniUserId)`:

1. Если слот `sys_omniuserid` пустой, завершение пропускается.
2. Через `agentApi.getDialogId(omniUserId, customerId)` получается `Response` с идентификатором диалога.
3. Вызывается `agentApi.finishDialog(dialogId, "Call end", 5)`.
4. Ошибки поиска или завершения логируются и перехватываются.

События `end` для типов `1` и `16` сами по себе не вызывают эту функцию.

#### Webhook в микросервис

Все события отправляются HTTP POST на `${microserviceUrl}/webhook`, таймаут запроса — **25 секунд**. В приведённых ниже примерах идентификаторы условные.

Ответ бота:

```json
{
  "callId": "call-123",
  "sessionId": "session-123",
  "event": "reply",
  "text": "Ответ бота",
  "messageType": 1
}
```

Завершение звонка (для сообщения типа `1` поле `messageType` будет равно `1`):

```json
{
  "callId": "call-123",
  "sessionId": "session-123",
  "event": "end",
  "messageType": 16
}
```

Подключение оператора:

```json
{
  "callId": "call-123",
  "sessionId": "session-123",
  "event": "operator_connected",
  "operator": "Иван Иванов",
  "target": {
    "topic": "Отключение ЭЭ",
    "groups": [{ "id": 301, "name": "Отключение ЭЭ" }]
  },
  "text": "Перевожу Ваш звонок на специалиста информационно-справочного центра.",
  "messageType": 18
}
```

`text` в событии `operator_connected` берётся из `routingText`, а не из исходящего сообщения. Если `routingText` не задан, при сериализации JSON поле с `undefined` будет отсутствовать.

Ошибка отправки webhook логируется и перехватывается, повторная отправка не реализована. После неудачной отправки `operator_connected` попытка завершить диалог всё равно выполняется. Ошибки верхнего уровня логируются в `.catch()`, а `.finally()` всегда вызывает `resolve({})`.

#### Настройки исходящего агента

| Настройка | Использование в текущем коде |
|-----------|-----------------------------|
| `microserviceUrl` | Базовый URL микросервиса; к нему добавляется `/webhook`. |
| `customerId` | Проект для `agentApi.getDialogId()`. |
| `routingText` | Текст в событии `operator_connected`. |
| `routingTopics` | Объект соответствия точных значений слота `theme` группам. |
| `channelId`, `slots` | Извлекаются из настроек, но далее не используются. |
| `channelAuthToken`, `callIdSlotId`, `sessionIdSlotId` | Есть в примере JSON, но скрипт их не читает. Идентификаторы слотов звонка и сессии заданы константами в коде. |

**2. В настройках jsagent для обработки входящих сообщений** в поле "Дополнительные настройки агента" указать:

```json

  "incoming_api": "http://<HOST>/webhooks/integration_channel/<CHANNEL_ID>",
  "authorization_token_incoming": "<INCOMING_TOKEN>"
```

**\<HOST\>** — ChannelService.Host, например `opbot-channels:8082`
**\<CHANNEL_ID\>** — Id канала

### Маппинг сообщений

| messageType | Webhook event | Действие |
|-------------|---------------|----------|
| 1 | `reply` | Вернуть текст ответа бота |
| 1 (любой признак завершения из раздела «Обработка типов сообщений») | `end` | Завершить звонок |
| 16 | `end` | Завершить звонок |
| 18 | `operator_connected` | Перевод на оператора + finishDialog |
