# Порядок работы с CT

Этот документ дополняет [AGENTS.md](../AGENTS.md). Для выбора каталога используйте
[карту проекта](PROJECT_MAP.md), для контрактов платформы — `agent_docs/`.
Команды ниже рассчитаны на PowerShell и запускаются из корня репозитория,
если явно не указано другое. Используйте только уже доступные инструменты
и зависимости.

## Перед изменениями

1. Выполните `git status --short`, определите уже изменённые и новые файлы.
   Не откатывайте и не перезаписывайте изменения, не относящиеся к задаче.
2. Определите заказчика, роль агента и endpoint. Прочитайте README нужной папки
   и 1–3 ближайшие реализации вместе с настройками.
3. Найдите существующие инструкции: `rg --files --hidden -g AGENTS.md -g '!.git' -g '!node_modules'`.
4. Сверьте нужные методы с `agent_docs/methods.json`, модели с
   `agent_docs/models.md`, глобальные объекты с `agent_docs/keywords.md`.
5. Для нового агента копируйте существующий образец; старый агент меняйте,
   когда задача явно требует его изменения. Не создавайте вымышленный Task ID.

Ссылка на `scripts/.Example-1/` не соответствует текущему дереву. Реальные
образцы HTTP-интеграций находятся в `Sigurd/Шаблоны агентов запросов/`;
для других типов используйте ближайшего агента того же назначения.

## Контракты реализации

- Диалоговый агент возвращает `ReplyMessage[]` через `resolve`; preprocessor
  и postprocessor — `resolve(message)`, канальный адаптер — `resolve({})`.
  У иных hook-endpoint свои контракты: сверяйтесь с `agent_endpoints.md`.
- Успешная ветка и обработчик ошибки должны завершать выполнение через `resolve`.
  Используйте принятый в соседних агентах шаблон `.then(...).catch(...)`.
- Для обычных сообщений учитывайте `message_type`. У события `200` имя находится
  в слоте `domain_event_type`. Специализированный подписчик событий может
  получать только события — не добавляйте ему текстовую ветку без необходимости.
- Состояние диалога не должно зависеть от переменной предыдущего запуска:
  используйте предусмотренные образцом слоты или нужную область `agentStorage`.
- URL, ID агентов, коды статей и прочие параметры окружения задавайте через
  `agentSettings`. Для секретов учитывайте принятый в реализации доступ через
  `agentParams`/Vault. В документах и новых примерах используйте заглушки.
- Используйте глобальный `axios`, `agentApi` и `logger.info` / `logger.error`.
  Не переносите авторизационные заголовки и полные пользовательские данные
  в новые диагностические сообщения.
- У JS-модулей общая область выполнения: следите за порядком подключения
  и именами. Разбиение больших агентов не обязательно: лимита размера скрипта нет.
  Модули можно использовать для выделения изолированной логики; порядок подключения
  и ограничение числа модулей описаны в `agent_docs/modules.md`.
- Новый README агента должен содержать описание и таблицу `Task / Entrypoint /
  Customer`; также опишите входные слоты, настройки, выход и поведение при ошибке.

## Проверки без запуска в платформе

У репозитория нет общей команды проверки. Выбирайте проверки изменяемой части.
Проверка синтаксиса не подтверждает корректность API, переходов и слотов.

Для выбранного JS-файла можно выполнить `node --check`, передав его реальный
путь в кавычках. Это проверяет синтаксис без исполнения, но не знает глобальные
объекты CraftTalk. Не запускайте обычный агент командой `node <файл>`.
JSON проверяйте парсером, не выводя содержимое настроек и секреты в консоль.

### Sigurd: существующие проверки идентификации

В текущем рабочем дереве есть проверки на встроенном `node:test`,
с подменёнными `axios`, `agentApi` и другими глобальными объектами:

```powershell
node --test 'Sigurd/Агенты интеграций/Идентификация общая/identification.test.cjs'
node --test 'Sigurd/Агенты интеграций/Приборы учета/Прием показаний/identification.test.cjs'
```

Проверяйте наличие файлов в своей копии. Запускайте соответствующий набор
при изменении идентификации; для других агентов используйте подходящие сценарии
с подменой внешних вызовов. Проверяйте успешный ответ, отсутствие данных,
ошибку запроса и корректное завершение/переход.

### Модульный GPT: сборка и тесты

Рабочий каталог:

```powershell
Push-Location 'Craft/jsagent-scripts-main-scripts-gpt/scripts-gpt/gpt-modular'
```

При изменении core выполните `bash build.sh` из этого каталога и проверьте
изменения `gpt_core.js`. Скрипт собирает `modules/core/[0-9]*.js` в порядке имён;
модели и клиентские скрипты в эту сборку не входят.
Не рассчитывайте на автоматический pre-commit: упомянутого в README каталога
`.githooks` в текущем дереве нет.

Если локальные зависимости уже доступны:

```powershell
npm test
# Или один подходящий файл:
npm test -- __tests__/core/slots.test.js
```

`npm test` исключает `__tests__/e2e/`. Отдельная команда `npm run test:e2e`
требует работающих jsagent и craftgpt, настроенного окружения и может выполнять
реальные LLM-запросы. Условия описаны в
[E2E README](../Craft/jsagent-scripts-main-scripts-gpt/scripts-gpt/gpt-modular/__tests__/e2e/README.md).
Пропущенные из-за отсутствия окружения E2E-тесты не считайте проверенным поведением.

После работы вернитесь в корень:

```powershell
Pop-Location
```

Если `bash`, Vitest или зависимости отсутствуют, укажите это в результате.
Не используйте `npm install`, `npm ci`, `pip install` или `npx`, способный
скачать отсутствующий пакет. Клиентские копии `gpt_core.js` обновляйте только
в рамках задачи, с проверкой совместимости модели и клиентских переопределений.

### Python: история диалога

Для рендеров есть локальные unittest-проверки:

```powershell
Push-Location 'Истории диалога'
python -m unittest discover -s test/render_test -p 'test_*.py'
Pop-Location
```

Команда требует доступного Python и импортируемых зависимостей.
Не выполняйте notebook или API-клиент для проверки форматирования рендера.
Утилиты Excel проверяйте на подходящем локальном входном файле после чтения
их путей и побочных действий.

## Импорт базы знаний

`Craft/Создание статей/scripts/import_from_excel.py` изменяет данные через API.
Флаг `--limit 2` ограничивает строки, но выполняет импорт и публикацию;
это не режим без записи, несмотря на формулировку старого README.
Анализ репозитория и локальные проверки не требуют его запуска.
Для задачи импорта следуйте локальному workflow, используя согласованные
проект, каталог, исходный Excel и источник токена `CRAFTTALK_TOKEN`.

## Завершение задачи

Проверьте `git diff --check`, список изменённых файлов и diff своей части.
Сохраните UTF-8 и местный стиль, обновите связанный README/настройки при изменении
контракта. Для документации достаточно проверить пути, ссылки и соответствие
команд реальной структуре; запускать продуктовые агенты для этого не нужно.

В результате укажите, что изменено, какие проверки выполнены и что осталось
непроверенным из-за отсутствия окружения. Не включайте чужие изменения в коммит
и не создавайте коммит или публикацию без соответствующей задачи пользователя.
